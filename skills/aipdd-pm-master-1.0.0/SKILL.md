## 通用交互协议 / Universal Interaction Protocol

所有交互式技能统一遵循以下协议（原文来自 workshop-facilitation，合并后仅保留一份）：
All interactive skills follow this protocol (originally from workshop-facilitation; kept once after merging):

### 核心原则 / Core Principles

1. **一次一问 / One question at a time**：每轮对话只问一个问题，等待用户回答后再继续 / Ask exactly one question per turn and wait for the answer.
2. **会话预告 / Session preview**：开始前告知预计时长与问题数量 / State the expected duration and question count up front.
3. **三种进入模式 / Three entry modes**：
   - **引导式（Guided）**：逐个提问，根据回答逐步构建建议（推荐）/ Ask step by step and build recommendations from the answers (recommended).
   - **情境粘贴（Context dump）**：用户一次性提供已知背景，跳过冗余提问 / The user dumps known context at once; skip redundant questions.
   - **最佳猜测（Best guess）**：用户不提供信息，按最常见情境给出高价值建议，并标注假设 / No info provided; give high-value advice for the most common case and flag assumptions.
4. **进度可见 / Visible progress**：每轮显示进度标签，如「背景 Q1/8」「评分 Q2/5」/ Show a progress label each turn, e.g. "Context Q1/8", "Scoring Q2/5".
5. **决策点编号建议 / Numbered decision options**：仅在需要选择时给出编号选项（2-5 个），并附简洁说明 / Offer numbered options (2–5) with brief descriptions only when a choice is needed.
6. **选项解析 / Option parsing**：接受 `#1`、`1`、`1和3`、`1,3` 或自定义文本，支持多选 / Accept `#1`, `1`, `1和3`, `1,3`, or custom text; multi-select supported.
7. **上下文感知 / Context-aware**：基于已答内容推进，不重复提问已解决的问题 / Build on answered content; never re-ask resolved questions.
8. **中断安全 / Interruption-safe**：被元问题打断时（如"还剩多少题？"），直接回答并恢复流程；用户说停止/暂停时立即停止，等待明确恢复指令 / Answer meta-questions directly and resume; stop immediately on stop/pause and wait for explicit resumption.
9. **快速路径 / Fast path**：用户要求一次性输出时，跳过多轮对话直接给出浓缩结果 / Skip the dialog and give a condensed result when the user asks for one-shot output.
10. **收尾 / Wrap-up**：结束时输出清晰总结、已做决策清单；若使用最佳猜测模式，附「待验证假设」列表 / End with a clear summary and decision list; attach an "assumptions to verify" list under best-guess mode.

### 常见陷阱 / Common Pitfalls

- 同一轮问多个问题 / Asking multiple questions in one turn
- 每个回答后都提供建议（造成交互拖沓）/ Giving advice after every answer (draggy interaction)
- 使用简写标签而不给通俗化问题 / Using shorthand labels without plain-language questions
- 隐藏进度，让用户不知道还剩多少 / Hiding progress so users don't know what's left
- 忽略用户已选选项或自定义方向 / Ignoring chosen options or custom directions
- 最佳猜测模式下不标注假设 / Not flagging assumptions in best-guess mode

# 第一部分：产品思维 / Part 1: Product Thinking

## 1.1 第一性原理分解器 / First Principles Decomposer

**触发词**：第一性原理、from scratch、我们在假设什么、拆解、原子、基本真理、埃隆方法、推倒重来、挑战假设

**适用场景**：设计新产品/功能；复杂问题卡壳；现有方案过于复杂；需要挑战假设；启动任何新项目。

### 核心概念 / Core Concepts

把问题分解到不可再分的基本真理，再自底向上重建解决方案。避免"按惯例做事"的思维惯性。

### 应用流程（三阶段）/ Application Flow (Three Phases)

**阶段 1：识别假设**
- 提问："我在假设什么是真的，但可能并非如此？"
- 列出当前方案中隐含的每一个假设

**阶段 2：分解到原子**
- 对每个假设追问："这里最基本的事实是什么？"
- 持续问"为什么"直到触及基石事实

**阶段 3：从真理重建**
- 仅从验证过的基本事实出发，提问："满足核心需求的最简方案是什么？"

### 交互流程 / Interaction Flow

1. 澄清问题（最多 1-2 个问题）
2. 列出假设——展示被视作理所当然的假设及其挑战
3. 分解到基本事实——展示原子真理
4. 重建方案——自底向上构建
5. 对比——展示新方案与传统方案的差异

### 输出模板 / Output Template

```
问题：[陈述的问题]

识别出的假设：
1. [假设] → 挑战：[为何可能错误]
2. [假设] → 挑战：[为何可能错误]

基本真理：
• [基石事实 1]
• [基石事实 2]
• [基石事实 3]

重建方案：
[仅从基本事实构建的新方案]

与传统方案对比：
[与显而易见方案的差异]
```

### 示例触发 / Example Triggers

- "用第一性原理拆解我们的家长沟通问题"
- "我想从头重新思考我们做 [X] 的方式"
- "我们对 [问题] 的哪些假设可能是错的？"

## 1.2 倒置策略师 / Inversion Strategist

**触发词**：倒置、反转、反过来想、如何保证失败、避免失败、什么不该做、Munger、反目标

**适用场景**：制定计划前识别失败路径；检验方案漏洞；目标达成前先排除致命错误。

### 核心原则 / Core Principles

"永远倒置，始终倒置。"——卡尔·雅可比

不问"如何实现 X？"，而问"什么能保证我实现不了 X？"然后系统性地避开这些事。

### 应用流程 / Application Flow

1. **陈述目标**
2. **倒置**："什么会保证失败？"
3. **列出失败路径**（7-10 条，既含明显也含隐蔽的）
4. **分类**：致命 / 有害 / 烦人
5. **转化为规避策略**
6. **建立反清单**

### 输出模板 / Output Template

```
目标：[想要的结果]
倒置问题："我如何保证在[目标]上失败？"

失败路径：

🔴 致命：
• [路径] → 规避方式：[策略]

🟡 有害：
• [路径] → 规避方式：[策略]

🟢 烦人：
• [路径] → 规避方式：[策略]

反清单：
□ 绝不 [行为]
□ 绝不 [行为]

正清单：
□ 始终 [失败行为的反面]
□ 始终 [失败行为的反面]
```

### 芒格智慧 / Munger Wisdom

"长期优势往往来自持续地不犯傻，而不是试图非常聪明。"
"告诉我我会死在哪里，我就永远不去那里。"

## 1.3 意图探索器 / Intent Explorer

**触发词**：意图、探索意图、我们应该做什么、真正的问题是什么、探索这个想法、用户研究、发现、需求落地

**适用场景**：新功能启动但用户问题定义不清；目标模糊且利益相关方意见不一；高 stakes 决策（意图搞错的代价高）。不适合：可复现的 bug 修复、已有明确成功标准的小任务、纯实现类问题。

### 核心概念 / Core Concepts

通过结构化对话探索问题/想法背后的意图，产出一份精确到 AI 代理无需猜测即可执行的意图规格（intentSpec）。核心是探索"做什么"和"为什么"，而非"怎么做"。

### 硬性规则 / Hard Rules

- **综合而非转录**：把原始回答提炼为产品语言
- **先验证再落盘**：把完整意图规格草稿交给用户批准后再写入
- **不做方案设计**：只探索意图，不涉及实现

### 交互模型（关键）/ Interaction Model (Key)

这是对话式技能，每个问答为一轮：
1. 每轮只问一个问题（2-4 个选项 + "其他"自由输入）
2. **停止。等待用户回答。**
3. 吸收回答，基于所学调整下一问
4. 重复；每轮之间可用 1-2 句话简要综合以显示跟踪

### 进入方式 / Entry Modes

1. 询问探索深度：
   - **快速**——范围明确、问题已知（约 6-8 个问题）
   - **深入**——目标模糊、全新领域、高 stakes（约 15-20 个问题）
2. 进入所选模式

### 快速模式：JTBD 聚焦探索（约 6-8 个问题）/ Quick Mode: JTBD-Focused Exploration (~6–8 questions)

按顺序覆盖主题（每轮一问，已答主题可跳过）：
- **情境与触发**——为什么现在这是优先级？
- **谁**——谁有这个问题？角色/背景？
- **功能任务**——此人想完成什么？（格式："帮我 [动词] [对象]"）
- **情感维度**——他们想有什么感受？（格式："让我感觉 [情绪]"）
- **社会维度**——他们想被如何看待？（如情境不相关可跳过）
- **当前替代方案**——他们现在怎么做？（真实竞争，非品类竞争：Netflix 的对手是睡眠，不只是 Hulu）
- **残余痛点**——这些替代方案的挫败点在哪？
- **期望结果**——可衡量的成功是什么样？（追问 2-3 个具体标准）

### 综合输出 / Consolidated Output

1. **任务陈述**："当 [情境]，我想 [动机]，以便 [结果]"
2. **进展力评估**：评估推力+拉力 vs 焦虑+习惯
3. **机会评分**：评估重要性与当前满意度

将综合结果展示给用户确认："这准确捕捉了意图吗？"若不准确，询问修正点后重新验证。

## 1.4 JTBD 工作台 / Jobs-To-Be-Done

**触发词**：JTBD、用户任务、客户动机、用户需求、为什么买、真正的问题

**适用场景**：理解用户"雇佣"产品的真实任务；超越功能层面理解功能/情感/社会动机；用户研究访谈设计；定位与产品定义前的研究。

> 本技能合并自原 jtbd-analyzer（框架分析）与 jobs-to-be-done（结构化研究）两个技能，二者视角互补。

### 核心概念 / Core Concepts

客户不买产品，他们"雇佣"产品来完成一项任务。

"人们不想要四分之一英寸的钻头。他们想要四分之一英寸的孔。"
实际上：他们想要一个架子 → 用来展示照片 → 为了对家庭感到自豪。

### 三类任务维度 / Three Job Dimensions

| 维度 | 问题 | 格式 |
|---|---|---|
| **功能** | 需要完成什么任务？ | "帮我 [动词] [对象]" |
| **情感** | 我想有什么感受？ | "让我感觉 [情绪]" |
| **社会** | 我想被如何看待？ | "帮我被看作 [特质]" |

### 应用流程 / Application Flow

1. **任务陈述**："当 [情境]，我想 [动机]，以便 [结果]"
2. **为每类用户映射全部 3 个维度**
3. **找出真实竞争**：还有什么能完成这个任务？（Netflix 与睡眠竞争，不只是 Hulu）
4. **优先级**：哪些任务最关键且最未被满足？

### 结构化的痛点与收益（Jobs 框架）/ Structured Pains & Gains (Jobs Framework)

对每个任务维度，进一步拆解：

**痛点（Pains）**：
- 挑战：完成任务过程中遇到的困难
- 成本：时间、金钱、精力的消耗
- 常见错误：用户常犯的错误
- 未解决的问题：替代方案留下的空白

**收益（Gains）**：
- 期望：用户希望得到的结果
- 节省：时间/金钱/精力上的节省
- 采纳因素：决定是否换用方案的因素
- 生活改善：任务完成后的生活质量提升

### 输出模板 / Output Template

```
产品：[分析对象]

对 [用户类型]：
任务："当 [情境]，我想 [动机]，以便 [结果]"

📋 功能：[要完成的任务]
💜 情感：[期望感受]
👥 社会：[期望形象]

替代方案：[还有什么能做这件事？]
未被满足：[哪部分做得不够好？]
优先级：关键 / 重要 / 可有可无
```

### 关键访谈问题 / Key Interview Questions

1. "你做 [动作] 的时候想完成什么？"
2. "带我走一遍你上次需要 [任务] 的过程"
3. "如果 [产品] 不存在，你会怎么做？"
4. "你现在做 [任务] 的哪些方面让你恼火？"

## 1.5 预 mortem 分析师 / Pre-Mortem Analyst

**触发词**：预 mortem、想象这个失败了、可能出什么问题、风险分析、上线前、压力测试、什么会杀死这个

**适用场景**：项目启动前的风险排查；重大发布前的压力测试；新方案验证。

### 为什么预 mortem 优于风险评估 / Why Pre-Mortem Beats Risk Assessment

**风险评估**："什么可能出错？" → 乐观偏差会过滤答案
**预 mortem**："6 个月后，它已经失败了。为什么？" → 释放诚实的分析

研究显示：预 mortem 能提升问题识别率 30%。

### 应用流程 / Application Flow

1. **设定场景**："现在是 [日期]。这个项目彻底失败了。"
2. **头脑风暴原因**：列出 10+ 个失败原因（不做过滤）
3. **分类**：人员、流程、技术、外部
4. **评级**：可能性 × 影响（高/中/低）
5. **预防**：前 3 名配具体缓解行动
6. **监控**：定义早期预警信号

### 输出模板 / Output Template

```
项目：[名称]
失败场景："现在是 [日期]。[项目] 已彻底失败。"

失败原因：

👥 人员：[原因] - 可能×影响：高/高 | 预防：[x] | 预警：[y]
⚙️ 流程：[原因] - 可能×影响：中/高 | 预防：[x] | 预警：[y]
💻 技术：[原因] - 可能×影响：低/高 | 预防：[x] | 预警：[y]
🌍 外部：[原因] - 可能×影响：中/中 | 预防：[x] | 预警：[y]

TOP 3 优先项：
1. [风险] → [具体行动]
2. [风险] → [具体行动]
3. [风险] → [具体行动]

需监控的预警信号：
□ [早期指标 1]
□ [早期指标 2]
```

### 常见失败类别 / Common Failure Categories

| 类别 | 常见原因 |
|---|---|
| **人员** | 关键人物离开、技能缺口、目标不一致、支持度低 |
| **流程** | 激进时间线、范围蔓延、依赖问题 |
| **技术** | 无法扩展、集成失败、安全漏洞 |
| **外部** | 市场转变、竞争对手行动、监管变化 |

## 1.6 跨行业迁移引擎 / Cross-Pollination Engine

**触发词**：跨行业、跨界、X 会怎么解决、借鉴想法、我们能学什么、跳出框框、迪士尼/苹果/亚马逊会怎么做、不同行业、偷师

**适用场景**：创新方案枯竭；需要差异化思路；把成熟行业已验证的方案迁移到本领域。

### 核心洞察 / Core Insights

大多数"创新"就是把一个领域已验证的解决方案应用到另一个领域。
- 阻力轮 → 旱冰鞋
- 游戏 XP 系统 → 多邻国
- 酒店礼宾 → 软件新用户引导

### 应用流程 / Application Flow

1. **定义核心任务**（剥离行业背景）

# 第二部分：产品策略 / Part 2: Product Strategy

## 2.1 海拔与地平线框架 / Altitude & Horizon Framework

**触发词**：晋升总监、思维层次、战略视野、团队方向不清、上下文级联

**适用场景**：理解 PM 晋升总监后真正变化的是什么；诊断哪个转型区在制造摩擦；组织方向模糊时应用上下文级联。

### 核心概念 / Core Concepts

区分总监级思维与 PM 思维的双轴模型：**海拔**（视野多宽）与**地平线**（看多远）。这不是资历等级——PM 在自己的角色正确海拔上工作就是优秀；总监在 PM 海拔上工作则是失职。

**海拔——范围**：
- **PM 海拔**：贴近地面。客户问题、单个功能、冲刺优先级、具体团队动态
- **总监海拔**：高层视角。产品组合、跨职能系统、组织动态、预算分配、市场定位
- 转变不是失去对客户的共情——而是拉远看整家餐厅，而不只是一张桌子

**地平线——时间**：
- **PM 地平线**：天、周、冲刺。最多一个季度
- **总监地平线**：季度为起点。年度规划周期、多年战略、市场变迁
- 总监为产品生态一年后应处的位置做规划，然后倒推

### 服务员 vs 餐厅经营者 / Server vs Restaurant Owner

| 维度 | PM（服务员） | 总监（餐厅经营者） |
|---|---|---|
| 关注点 | 单个食客体验 | 整个系统——人员、利润、菜单、供应商 |
| 权力 | 影响但无控制 | 组合决策、预算、资源分配 |
| 成功指标 | 七号桌满意 | 餐厅盈利、一致、可扩展 |
| 与客户关系 | 直接、日常、亲密 | 聚合模式、买家画像、市场群体 |
| 失败模式 | 忽视七号桌的需求 | 执着于七号桌的柠檬 |

### 四个转型区 / Four Transition Zones

PM → 总监需要跨越四个区域，多数人会在其中一两个卡住——诊断出哪个是杠杆点：

**区 1——思维海拔**
- 停止：直接解决单个客户问题
- 开始：设计解决一类问题的系统和团队

**区 2——角色转变**
- 停止：执着于单个用户画像和日常客户触点
- 开始：以买家画像、市场群体、组织利益相关者、高管动态思考

**区 3——英雄综合征恢复**
- 停止：做那个救场并赢得表扬的人
- 开始：从团队成功中获得满足——你的产品是团队，不是路线图

**区 4——方向创造**
- 停止：等待上方给出明确方向才行动
- 开始：创建上下文级联，把公司战略翻译成团队清晰度，即使输入不完整

### 命名失败模式 / Named Failure Modes

**英雄综合征**：跳进去直接解决问题、贴近战术工作、想要个人胜利的可见性。原因：PM 被训练成乐于助人。总监得不到那么多表扬，就退回旧的奖励回路。代价：作为总监表现欠佳，同时过度发挥高级 IC 职能；团队因你在挡路而不成长。

**流程过敏**：抵制共享结构、让高绩效 PM 各自为政。原因：PM 天然抵制官僚。早期总监的放任看起来像"优秀领导力"。代价：营销、财务、领导层无法综合不一致的输出。没有共享流程，团队就成了"满屋乱砸玻璃的猴子"。

**讨好型领导**：想让团队喜欢你、回避硬反馈、对利益相关方有求必应。原因：让你成为优秀 PM 的技能（倾听、共情、响应）在组织规模下成了负债。代价：把"受欢迎"当"有效"。尊重来自清晰与硬决策，而非友善。

**即时满足陷阱**：读领导力书籍、收集证书、问"我要怎么做才能升职？"。原因：PM 擅长优化，试图走捷径跳过经验要求。代价：总监就绪需要实战故事和经历过谦逊。你可以学到词汇的流利，但学不到角色的就绪。

**非黑即白思维**："这看起来是明摆着的决定。""为什么不能都做？""为什么这里这么政治？"原因：PM 在更干净的问题空间运作，因果关系更清晰。总监决策涉及竞争约束、信息有限、组织动态。代价：低置信度的快速决策制造下游混乱。灰度不是领导力失败——它是真实的地形。

### 上下文级联图 / Cascading Context Map

当组织方向模糊或缺失时，总监不等待——他们级联。

**六步**：
1. **倾听顶层战略**——QBR、公司信息、高管沟通
2. **提取领导层陈述的关键优先项**——识别 3-5 个主题，不是 20 个要点
3. **映射第二层**："我们的事业部如何实现这些目标？"
4. **映射第三层**："我们的产品组合如何达成？"
5. **映射第四层**："我的团队具体负责什么来驱动第三层成功？"
6. **向团队传达级联**——不仅做什么，还有为什么向上连接

**解决的问题**：团队"在荒野中游荡"——交付的工作与战略脱节，因为上下文从未被翻译给他们。

**核心原则**：即使上方指令不完整，总监的职责也是向下填补缺口。等待完美清晰是 PM 习惯；创造不完美但有用的清晰是总监技能。

### 应用 / Application

**作为 PM（转型前）**：
1. 识别你最弱的转型区——先不行动，只是知道该观察什么
2. 用与经理的 1 对 1 练习区 4："我的工作如何连接业务战略？我没看到的组织背景是什么？"
3. 观察英雄综合征习惯：你是否跳进那些本可用教练方式解决的事？
4. 别在 PM 角色过度投资总监思维。全力服务当前职责——需要时总监海拔自然会出现

**作为新任总监**：
1. **前 30 天**：绘制你的新海拔与地平线图。新利益相关者是谁？这个组织的季度到年度规划周期实际什么样？
2. **前 60 天**：识别英雄综合征触发点。何时感到想直接跳进去而不是教练？
3. **前 90 天**：运行第一次上下文级联。即使公司战略不清晰，做你最好的翻译并与团队分享
4. **持续**：出现摩擦时，命名它属于哪个转型区。先诊断后开方

## 2.2 机会-解决方案树 / Opportunity Solution Tree, OST

**触发词**：机会树、OST、从需求到方案、功能工厂、结构化探索

**适用场景**：利益相关方提出功能需求或产品计划；启动新领域探索；澄清模糊的 OKR/战略目标；决定先解决哪些问题；对齐团队正在驱动的成果。不适用：问题已验证（直接做方案测试）、战术 bug 修复、利益相关方已指定方案（先解决对齐问题）。

### 核心概念 / Core Concepts

OST 是可视化框架（Teresa Torres《持续发现习惯》），连接四层：
1. **期望成果**（业务目标或产品指标）
2. **机会**（客户问题、需求、痛点、欲望——能驱动成果的）
3. **方案**（解决每个机会的方式）
4. **实验**（验证方案）

**结构**：
```
         期望成果 (1)
              |
    +---------+---------+
    |         |         |
 机会    机会    机会 (3)
    |         |         |
  +-+-+     +-+-+     +-+-+
  | | |     | | |     | | |
 S1 S2 S3  S1 S2 S3  S1 S2 S3 (共9个方案)
```

### 反模式 / Anti-Patterns

- 不是功能清单：机会是客户面临的问题，不是"我们需要深色模式"
- 不是方案优先：不要从"我们应该建 X"开始——从"客户在 Y 上挣扎"开始
- 不是瀑布计划：OST 是发现工具，不是项目计划
- 不是一次性活动：随着实验学习不断演进

### 两阶段应用流程 / Two-Phase Application Flow

**阶段 1：生成 OST**——提取期望成果 → 识别机会 → 映射方案
**阶段 2：选择 POC**——评估方案 → 推荐最佳起点

### 交互问题脚本 / Interaction Question Script

**问题 1：提取期望成果**
"这个计划的期望成果是什么？（要推动的业务或产品指标是什么？）"
1. **收入增长**——"提高 ARR、扩展现有客户收入、新收入流"（常见于规模化产品）
2. **客户留存**——"降低流失、提高激活、提升参与/粘性"（常见于有留存问题的成熟产品）
3. **客户获取**——"提高注册量、试用转化、新用户增长"（常见于早期或增长产品）
4. **产品效率**——"降低支持成本、缩短价值实现时间、改善运营指标"（常见于优化运营的成熟产品）

**问题 2-4（依序）**：识别机会选项（客户问题）→ 映射每个机会下的潜在方案 → 选择 POC 时按可行性、影响、市场契合度评估。

## 2.3 优先级顾问 / Prioritization Advisor

**触发词**：优先级、RICE、ICE、Kano、MoSCoW、先做什么、框架选择

**适用场景**：首次选择优先级框架；现有框架不适用需要更换；对齐利益相关方优先级流程；新 PM 入职团队实践。不适用：已有可用框架（别修没坏的东西）、一次性决策（框架用于周期性优先级）、替代战略愿景（框架不能告诉你建什么）。

### 核心概念：优先级框架全景 / Core Concept: The Prioritization Framework Landscape

**评分类框架**：
- **RICE**（触达 Reach、影响 Impact、置信 Confidence、投入 Effort）——数据驱动，需要指标
- **ICE**（影响 Impact、置信 Confidence、易做 Ease）——轻量、凭感觉打分
- **价值 vs 投入**（2x2 矩阵）——速赢 vs 战略赌注
- **加权评分**——自定义标准 + 利益相关方输入

**战略类框架**：
- **Kano 模型**——按客户满意度分类（基本、绩效、惊喜）
- **机会评分**——重要性与满意度差距评分
- **购买功能**——客户预算分配练习
- **MoSCoW**（必须有、应该有、可以有、不会有）——逼迫硬取舍

**情境类框架**：
- **延迟成本**——基于紧迫性（时效敏感功能）
- **影响映射**——目标驱动（功能与成果挂钩）
- **故事地图**——基于用户旅程（叙事流）

### 交互问题脚本（最多 4 个自适应问题）/ Interaction Question Script (up to 4 adaptive questions)

**问题 1：产品阶段**
1. **产品-市场契合前**——"探索 PMF；快速试验；不清楚客户要什么"（高不确定性，需速度）
2. **早期 PMF，规模化**——"找到初步 PMF；快速增长；加功能留存/扩展"（中不确定性，速度+质量平衡）
3. **成熟产品，优化**——"市场确立；增量改进；质量/功能竞争"（低不确定性，数据驱动）
4. **多产品/平台**——"产品组合；跨产品依赖；复杂利益相关方需求"（协调复杂度）

**问题 2：团队情境**
1. **小团队、资源有限**——"3-5 个工程师、1 个 PM，需残酷聚焦"（需简单快速框架）
2. **跨职能、对齐良好**——"产品、设计、工程对齐；目标清晰；协作好"（可用数据驱动框架）
3. **多利益相关方、不对齐**——"高管、销售、客户各有意见；需透明流程"（需共识构建框架）
4. **大组织、复杂依赖**——"多团队、共享路线图、跨团队依赖"（需协调框架）

**问题 3：决策需求**
1. **想法太多，不知追哪个**——"积压 100+ 项；需缩小到前 10"（需筛选框架）
2. **利益相关方优先级冲突**——"销售要功能、高管要战略赌注、工程要技术债"（需对齐框架）
3. **缺乏数据驱动决策**——"凭感觉排优先级；想要指标流程"（需评分框架）
4. **战略赌注 vs 速赢的硬取舍**——"平衡长期愿景 vs 短期客户需求"（需价值/投入框架）

**问题 4（情境相关）**：确认利益相关方动态后给出推荐框架 + 实施步骤。

## 2.4 Epic 假设 / Epic Hypothesis

**触发词**：epic 假设、if-then、假设驱动、小发现行动、可证伪

**适用场景**：早期功能探索（承诺完整路线图之前）；验证新能力的产品-市场契合；积压排序（已验证假设的 epic 更高优先级）；管理利益相关方预期（把工作框定为实验而非承诺）。不适用：已验证功能（直接写用户故事）、琐碎功能、实验不可行的场景。

### 核心概念：Epic 假设框架 / Core Concept: The Epic Hypothesis Framework

源自 Tim Herbig 的 Lean UX 假设格式：

**If/Then 假设**：
- **如果我们** [为目标画像执行 [动作或方案]]
- **为了** [目标画像]
- **那么我们将** [达成 [期望成果或任务]]

**小发现行动实验**：
- **我们将通过以下方式测试假设：** [实验 1] [实验 2]

**验证指标**：
- **如果在 [时间范围] 内观察到以下结果，则假设有效：** [定量指标] [定性指标]

### 为什么有效 / Why It Works

- **假设驱动**：迫使你陈述所相信的（且可能是错的）
- **成果导向**："那么我们将"强调用户收益，而非功能产出
- **实验优先**：全量建设前先轻量验证
- **可证伪**：明确成功标准使早期杀死坏想法成为可能
- **风险管理**：把 epic 当赌注，而非承诺

### 反模式 / Anti-Patterns

- 不是功能规格："建一个带 5 个图表的仪表盘"是功能，不是假设
- 不是保证承诺：假设可以（也应该）被证伪
- 不是产出导向："Q2 上线功能 X"跑偏了——它达成成果了吗？
- 不是无实验：跳过实验直接建设，就不是在测试假设

### 应用流程 / Application Flow

**步骤 1：收集背景**——问题理解、目标画像、JTBD、当前替代方案。缺背景先做发现访谈。

**步骤 2：起草 If/Then 假设**：
- "如果我们"要具体：不是"改进产品"而是"添加一键 Slack 通知"
- "为了"是清晰画像：不是"用户"而是"管理 3+ 分布式团队的远程项目经理"
- "那么我们将"是成果：不是"用户会有通知"而是"用户对任务分配响应快 50%"

示例：
- ✅ "如果我们为试用用户添加一键 Google 日历集成，那么 30 天内激活率将提升 20%"
- ✅ "如果我们为管理 1000+ 项的高级用户提供批量删除，那么清理任务耗时将减少 70%"
- ❌ "如果我们建一个仪表盘，用户就会用"（模糊、不可衡量）

**步骤 3：设计小发现行动实验**（原型+用户测试、礼宾测试、落地页测试、绿野仙踪测试、A/B 测试）

**步骤 4：定义验证指标**（时间范围 + 定量/定性可测成果）

## 2.5 Epic 拆解顾问 / Epic Breakdown Advisor

**触发词**：epic 拆解、用户故事拆分、垂直切片、Richard Lawrence、Humanizing Work

**适用场景**：把大 epic 拆成用户故事；确保垂直切片（端到端价值）而非水平切片（技术层）；识别可砍掉的低价值工作。

### 核心概念：三步流程 / Core Concept: Three-Step Process

1. **拆分前验证**：检查故事是否满足 INVEST 标准（"小"除外）
2. **应用拆分模式**：按顺序走 9 种模式直到一种适用
3. **评估拆分**：选择能揭示低价值工作或产生等量故事的拆分

### 9 种拆分模式（按顺序）/ Nine Splitting Patterns (in order)

1. **工作流步骤**——细的端到端切片，不是逐步切
2. **操作（CRUD）**——创建、读取、更新、删除各自成故事
3. **业务规则变体**——不同规则 = 不同故事
4. **数据变体**——不同数据类型/结构
5. **数据录入方式**——先简单 UI，后花哨 UI
6. **重大工作量**——"先实现一个 + 其余后续加"
7. **简单/复杂**——先核心最简版本，后变体
8. **延迟性能**——先"能跑"再"跑得快"
9. **拆出 Spike**——不确定性阻塞拆分时，限时调查

### 元模式（适用于所有模式）/ Meta-Patterns (apply to all patterns)

1. 识别核心复杂度
2. 列出所有变体
3. 把变体缩减为**一个完整切片**
4. 其他变体做成独立故事

### 为什么有效 / Why It Works

- 防止随意拆分：方法化清单防止猜测
- 保留用户价值：每个故事交付可观察价值
- 揭示浪费：好拆分暴露可降级的低价值工作
- 可重复：任何 epic 一致应用

### 交互问题脚本 / Interaction Question Script

**步骤 0：提供 Epic 背景**——标题/ID、描述或假设、验收标准（特别是多组 When/Then）、目标画像、粗略估算。

**步骤 1：INVEST 验证**（逐问确认）：
1. **独立？**——"这个故事能无硬技术依赖地被排期开发吗？"
2. **可协商？**——"这个故事留给团队协作发现实现细节的空间，而非预设方案吗？"
3. **有价值？**——"这个故事给用户交付可观察的价值吗？"（⚠️ 若失败则**停止**，不要拆分，与其他工作合并成有意义增量）
4. **可估算？**——"团队能相对估算这个故事吗？"（不能可能需要先 spike）
5. **可测试？**——"验收标准清晰吗？"

**步骤 2-3**：按 9 模式顺序匹配 → 评估拆分，优先能揭示低价值工作的拆分。

## 2.6 路线图规划 / Roadmap Planning

**触发词**：路线图、季度规划、半年规划、发布序列、roadmap

**适用场景**：年度或季度规划周期；产品战略会后（把战略翻译成路线图）；新利益相关方对齐；把现有功能驱动路线图重构为成果驱动。不适用：战术冲刺规划（用积压）、战略不清晰时（先做战略工作坊）、利益相关方期望日期承诺时（先管理预期）。

### 核心概念 / Core Concepts

路线图规划流程：收集输入（客户问题、业务目标、技术约束）→ 定义计划（带假设和成功指标的 epic）→ 优先级排序 → 序列化（按逻辑依赖排入发布/季度）→ 沟通（带战略叙事的路线图展示）。

### 路线图类型 / Roadmap Types

**现在/下一步/以后路线图**：
- 现在：当前季度（已承诺）
- 下一步：下季度（高置信）
- 以后：未来探索（低置信）
- 最适合：敏捷团队、不确定性、持续发现

**主题路线图**：按战略主题组织（"留存"、"企业扩张"、"移动体验"），最适合向高管展示战略意图。

**时间线路线图（季度）**：Q1：Epic A、B；Q2：Epic C、D……最适合资源规划、利益相关方沟通。

**功能路线图（反模式）**：无背景地罗列功能（"深色模式"、"SSO"）。失败原因：无战略叙事、未框定客户问题。

### 五阶段应用流程（1-2 周）/ Five-Phase Application Flow (1–2 weeks)

**阶段 1：收集输入（第 1-2 天）**
1. 回顾业务目标（OKR、战略计划）：公司今年前 3 优先项？哪些指标必须动？（收入、留存、获取、效率）→ 输出 3-5 个要优化的业务成果
2. 回顾客户问题（发现访谈、支持工单、NPS、流失调查）：前 3-5 个客户痛点？哪个影响最多客户？强度最高？→ 输出 3-5 个已验证客户问题
3. 回顾技术约束与机会：技术阻塞？（扩展、性能、安全）赋能投资？（平台升级、API 重写）→ 输出所需技术投资清单
4. 回顾利益相关方请求：分类为业务成果相关 vs 噪音

**阶段 2：定义计划**——把输入综合为 epic（每条带 If/Then 假设 + 成功指标，见 2.4）

**阶段 3：优先级排序**——用 2.3 优先级框架排名（按影响、投入、战略契合）

**阶段 4：序列化**——组织为发布/季度，尊重依赖，安排快速成功与战略赌注

**阶段 5：沟通**——用战略叙事展示（"我们为什么建这个"而非"我们建什么"），对高管呈现主题路线图

### 常见陷阱 / Common Pitfalls

- 把路线图当合同（它是战略计划，会按季度学习演进）
- 无战略叙事的纯功能清单
- 把路线图当甘特图（它是沟通工具，非时间表）

## 2.7 产品战略工作坊 / Product Strategy Session

**触发词**：产品战略、战略梳理、定位+问题+路线图一体化、年度战略

**适用场景**：启动新产品或重大计划；年度/季度战略规划周期；现有产品重新定位；新产品领导入职对齐。不适用：战略已清晰验证、战术功能补充（无需战略转变）、缺乏高管支持（战略不会落地）。

### 核心概念 / Core Concepts

结构化多阶段流程，把产品从战略模糊带到验证方向，编排四大模块：定位与市场背景 → 问题发现与验证 → 方案探索 → 路线图规划。

### 六阶段流程（2-4 周）/ Six-Phase Process (2–4 weeks)

**阶段 1：定位与市场背景（第 1 周，1-2 天）**
目标：定义目标客户、问题空间、差异化。
1. **运行定位工作坊**（90 分钟）——参与者：PM、产品领导、市场、销售 → 输出：定位陈述草稿
2. **定义 Proto Personas**（60 分钟）——PM、设计、客户接触团队 → 输出：1-3 个假设驱动画像
3. **映射 JTBD**（60 分钟）——PM、设计 → 输出：每个画像的 JTBD 陈述

**决策点 1：客户背景是否足够？**
- 是 → 进入阶段 2
- 否 → 额外发现：安排 5-10 场客户访谈，验证定位假设（时间影响：+1 周）

**阶段 2：问题框架与验证（第 1 周，3-5 天）**
1. **运行问题框架画布**（120 分钟，MITRE 方法）——PM、设计、工程负责人、客户成功 → 输出：精炼问题陈述 + HMW 问题
2. **创建正式问题陈述**（30 分钟）——PM → 输出：PRD/路线图用结构化问题陈述
3. **映射客户旅程**（可选，90 分钟）——问题跨多个触点/阶段时使用 → 输出：带痛点与机会的旅程图

**决策点 2：问题是否已验证？**
- 是 → 进入阶段 3
- 否 → 运行发现访谈计划，验证问题后才继续（时间影响：+1 周）

**阶段 3：方案探索（第 2 周，1-2 天）**
1. **生成机会-解决方案树**（OST）——按期望成果探索机会与方案
2. **选择 POC**——按可行性、影响、市场契合度推荐最佳起点

**阶段 4：路线图规划（第 2 周，3-5 天）**
1. **运行路线图规划流程**（见 2.6）
2. **与利益相关方评审**——跨职能验证优先项与排序

**决策点 3：路线图是否达成一致？**
- 是 → 进入阶段 5
- 否 → 针对分歧项做额外分析或取舍讨论

**阶段 5：战略文档化与沟通（第 3 周）**
1. **撰写战略备忘录**——定位陈述、目标客户、问题陈述、优先路线图、成功指标
2. **与利益相关方沟通**——向高管、团队、关键跨职能伙伴分享

**阶段 6：持续校准（第 3-4 周）**
1. 设置指标基线
2. 安排月度回顾——按学习调整路线图

### 常见陷阱 / Common Pitfalls

- 变成功能头脑风暴（战略工作坊是框定问题，不是罗列功能）
- 瀑布式规划（需内置反馈循环和迭代）
- 单人 PM 练习（需跨职能参与）
- 无高管支持就推进（战略不会落地）

## 2.8 推荐画布 / Recommendation Canvas

**触发词**：AI 产品方案、推荐画布、方案评估、向高管提案、AI 功能

**适用场景**：提议新的 AI 驱动产品或功能；向高管提案或争取预算/赞助；评估 AI 方案是否值得做；对齐跨职能利益相关方（产品、工程、数据科学、业务）；完成初步发现之后（需要背景才能填写）。不适用：琐碎功能、未做任何发现工作、作为实验的替代品。

### 核心概念：十大组件 / Core Concept: Ten Components

1. **业务成果**——对业务有什么好处？
2. **产品成果**——对客户有什么好处？
3. **问题陈述**——以画像为中心的框架
4. **方案假设**——带实验的 If/Then 假设
5. **定位陈述**——价值主张与差异化
6. **假设与未知**——什么可能证伪它？
7. **PESTEL 风险**——政治、经济、社会、技术、环境、法律
8. **价值论证**——为什么值得做
9. **成功指标**——衡量影响的 SMART 指标
10. **下一步**——战略后续步骤

### 应用流程 / Application Flow

**步骤 1：收集背景**——问题理解（用户研究、痛点）、画像清晰度（谁经历问题）、市场背景（竞争格局、品类定位）、业务约束（预算、时间线、战略优先项）。缺背景先做发现——画布综合洞察，不创造洞察。

**步骤 2：定义成果**
- **业务成果格式**：[方向] [指标] [成果] [背景] [验收标准]，例："12 个月内将企业客户的月经常性收入提升 15%"
- **产品成果格式**（客户视角，"我"而非"我们"）：例："将小企业主手工处理发票的时间减少 60%"
- 质量检查：可衡量？有时间限制？雄心但现实？

**步骤 3：框定问题**——用问题陈述的共情叙事（见 7.4 问题陈述章节）：2-3 句讲述画像故事。质量检查：有共情？（像用户的声音）；具体？（不是"用户想要更好的工具"而是"Sarah 每月花 8 小时……"）；已验证？（基于真实研究）

**步骤 4：定义方案假设**——If/Then 结构 + 小发现实验（见 2.4 Epic 假设）

**步骤 5：陈述定位**——用 Geoffrey Moore 格式（见 3.1）

**步骤 6：列出假设与未知**——什么可能证伪此方案？（技术限制、市场时机、用户接受度）

**步骤 7：PESTEL 风险扫描**——六个维度各列出影响（见 3.2）

**步骤 8：价值论证**——为什么值得做？（ROI、竞争护城河、平台赋能、风险降低）

**步骤 9：成功指标**——SMART 指标连接业务成果

**步骤 10：下一步**——验证实验优先级、时间线、决策者

### 常见陷阱 / Common Pitfalls

- 当成 PRD（这是战略框定，不是详细需求）
- 当成商业案例（它支撑商业案例，但需先验证）
- 当成功能清单（关注成果，不是能力）

## 2.9 六格故事板 / Storyboard

**触发词**：故事板、六格叙事、用户故事可视化、愿景沟通、stakeholder 对齐

**适用场景**：向利益相关方推介新产品/功能；对齐团队对用户价值的理解；测试产品想法是否引起情感共鸣；全员大会或投资人会议沟通愿景；建设前验证问题/方案契合。不适用：技术实现细节（用架构图）、用户问题琐碎或已知、替代用户研究（故事板展示洞察，不创造洞察）。

### 核心概念：六格结构 / Core Concept: Six-Cell Structure

基于经典叙事弧：主角 → 问题浮现 → "糟糕"时刻 → 方案出现 → "啊哈"时刻 → 方案后的生活。

### 应用流程 / Application Flow

**步骤 1：收集背景**——画像清晰度、问题理解、方案定义、期望成果。缺背景先做发现，不虚构画像或问题。

**步骤 2：回答 7 个故事板问题**（一次一个）：
1. 谁是这个问题的主角？（姓名、年龄、角色、背景）
2. 描述主角面临的挑战
3. 描述问题升级为重大麻烦的"糟糕"时刻
4. 方案如何进入主角的生活？
5. 描述主角使用方案并体验"啊哈"时刻
6. 使用方案后主角的生活是什么样？
7. 有特定视觉风格或渲染要求吗？（默认：粗马克笔草图，极简单色）

**步骤 3：撰写六格叙事**——按上答案起草。

**步骤 4：可视化每格**——为每格创建/描述画面：视觉元素、氛围（忙碌、压垮、释然）、工具（DALL·E、MidJourney、手绘）。

### 输出模板（每格）/ Output Template (per cell)

```
**格 1：介绍主角**
- [主角描述：人物、场景、背景]
- 例："Sarah，35 岁，自由平面设计师，在家办公同时推进 10 个客户项目"

**格 2：问题浮现**
- [主角面临的挑战及影响]
- 例："她淹没在发票追踪里——每月 8 小时在电子表格和邮件里追讨逾期付款"

**格 3：'糟糕'时刻**
- [问题升级为重大麻烦]
- 例："一个重要客户付款逾期 2 周。Sarah 因忙于设计忘了跟进。客户沉默了，她为现金流焦虑"

**格 4：方案出现**
- [方案如何引入 + 主角初步反应]
- 例："Sarah 发现 SmartInvoice——自动在最佳时间发送付款提醒的工具。她怀疑会不会太强硬，但决定试试"

**格 5：'啊哈'时刻**
- [主角使用方案体验突破]
- 例："两天后，Sarah 收到通知：'客户 XYZ 刚付款！'AI 定时提醒奏效了——无需尴尬的跟进电话。她感到解脱和掌控"

**格 6：方案后的生活**
- [解决方案后的改善状态]
- 例："Sarah 现在每月只花 30 分钟在发票上，而不是 8 小时。她重新拥有了夜晚，现金流可预测，焦虑消失"
```

### 常见陷阱 / Common Pitfalls

- 画成用户流程图（这是情感叙事，不是流程文档）
- 变成功能演示（关注用户成果，不是产品能力）
- 写成营销文案（真实叙事，不是炒作）

# 第三部分：市场与定位 / Part 3: Market & Positioning

## 3.1 定位陈述与定位工作坊 / Positioning

**触发词**：定位、定位陈述、价值主张、差异化、重新定位、Geoffrey Moore

**适用场景**：定义新产品或重大转向的定位；对齐高管/创始人/PM/市场战略；测试差异化是真实还是想象；写 PRD、发布计划、销售材料之前；重新定位现有产品（转型、市场变化）。不适用：内部工具（定位针对市场）、还在问题验证阶段（先确定问题再定位）、替代客户研究（定位综合洞察，不创造洞察）。

> 本技能合并自 positioning-statement（陈述框架）与 positioning-workshop（交互式发现流程），二者配合使用：工作坊负责发现，陈述负责产出。

### 核心概念：Geoffrey Moore 框架 / Core Concept: The Geoffrey Moore Framework

源自《跨越鸿沟》，定位分两部分：

**价值主张**：
- **为了** [目标客户]
- **他们需要** [未被满足的需求]
- [产品名]
- **是一种** [产品品类]
- **它** [收益陈述]

**差异化陈述**：
- **不同于** [主要竞争对手或替代方案]
- [产品名]
- **提供** [独特差异化]

### 为什么这个结构有效 / Why This Structure Works

- 迫使具体化：不能说"面向所有人"或"不同于所有竞争者"
- 暴露假设：填不上"不同于 X"，可能就没有可防御的差异化
- 聚焦成果而非功能："将流失率降低 40%"胜过"有分析功能"
- 品类锚定认知：说"是 CRM"vs"是工作流工具"会改变买家评估方式

### 交互工作坊流程（最多 5 个自适应问题）/ Interactive Workshop Flow (up to 5 adaptive questions)

**步骤 0：收集产品背景**——网站文案、现有定位陈述、客户证言/案例、销售异议或竞争输赢分析。重新定位时：当前定位、客户反馈/工单、竞争情报。无产品时：找 2-3 个竞品或类比产品做参照。

**问题 1：目标客户细分**
"基于已提供背景，你服务的主要客户细分是谁？"
1. **B2B：中小企业决策者**——"10-50 人的小企业主管理运营"（如 Gusto、QuickBooks）
2. **B2B：企业买家**——"500+ 人公司的 IT/产品负责人"（如 Salesforce、Workday）
3. **B2C：大众消费者**——"18-25 岁 Z 世代寻找预算工具"（如 Mint、Venmo）
4. **B2C：小众爱好者**——"追踪宏量和健身数据的爱好者"（如 MyFitnessPal、Strava）

**问题 2：未被满足的需求（JTBD 视角）**
"你的目标客户有哪些未被满足的需求或痛点，你的产品解决了它？"
1. **耗时的手工工作**——"每周 10+ 小时花在本该自动化的任务上"（发票处理、薪酬、报表）
2. **缺乏可见性或控制**——"看不到项目实时状态导致错过截止日期"（项目追踪、仪表盘）
3. **合规或风险负担**——"担心手工错误导致税务罚款或法律问题"（财务、HR 合规）
4. **代价高昂的低效**——"因流程缓慢或客户摩擦损失收入"（销售运营、客户引导）

**问题 3：产品品类**——"买家会把你的方案归类为什么品类？"（品类帮助或伤害你？有时创造新品类是战略性的但有风险）

**问题 4：收益**——"客户获得什么成果？"（说用户*得到*什么，不是说产品*有*什么）

**问题 5：竞争差异化**——"谁是你真正的竞争替代？（直接竞品 + 替代行为，如 'Excel' 往往才是真对手）"

### 质量检查清单 / Quality Checklist

- **目标具体性**：能向招聘官描述这个人吗？不能就收窄
- **需求清晰度**：这个需求有情感共鸣吗？还是空泛（"需要效率"）？
- **品类契合**：这个品类帮助你还是伤害你？
- **成果导向**：你说的是用户*获得*什么，而不是产品*拥有*什么
- **竞争诚实**：这是买家*真正*考虑的替代品吗？（不只是你希望他们对比的对象）
- **差异化实质**：竞争者 6 个月内能抄走吗？能就不是持久差异化
- **压力测试**：用一个真实买家或销售同事读一遍——他会被打动并理解吗？

### 反模式 / Anti-Patterns

- 不是口号："定位" ≠ "耐克：Just Do It"
- 不是功能列表：别说"提供 AI、自动化和集成"
- 不是空泛："为需要效率的企业" = 定位表演
- 不是愿景泡沫："革命性提升生产力"没有具体数字就是噪音

## 3.2 PESTEL 宏观分析 / PESTEL Analysis

**触发词**：PESTEL、宏观环境、市场进入、外部风险、政治经济分析

**适用场景**：进入新市场或新地区；战略规划（年度路线图、3-5 年规划）；评估变化环境中产品可行性；新产品计划风险评估；向高管或投资人提案（展示环境意识）。不适用：战术短期决策（用竞争分析）、外部因素稳定且已知、替代客户研究（PESTEL 是宏观不是微观）。

### 核心概念：六维框架 / Core Concept: Six-Dimension Framework

源自 Francis Joseph Aguilar 1967 年的 PEST 分析，扩展为六类：
1. **政治**：政府政策、稳定性、贸易法规、税收
2. **经济**：增长率、通胀、汇率、消费支出
3. **社会**：人口统计、文化趋势、生活方式变化、消费者态度
4. **技术**：进步、研发、自动化、数字化转型
5. **环境**：气候变化、可持续性、资源稀缺、法规
6. **法律**：合规、知识产权、劳动法、健康安全法规

### 应用流程 / Application Flow

**步骤 1：定义范围**——项目/产品名、分析目的（具体，如"评估欧盟上市可行性"而非"分析市场"）、地理范围、时间范围（PESTEL 因素会变，需声明范围）。

**步骤 2-7：逐维分析**，每维包含：
- **政策/趋势**：可能如何影响产品？
- **具体到你的产品**：不列通用政策——解释影响
- **可行动**：能否基于此洞察调整策略？

示例（政治）：
- "欧盟 AI 法案要求 AI 决策透明；我们的发票自动化必须解释推荐逻辑"
- "英国脱欧使英欧数据传输复杂化；可能需要独立基础设施"
- "欧盟数字服务税（营收的 3%）可能影响定价策略"

示例（经济）：
- "中小企业部门年增 5%；自动化工具需求强劲"
- "高通胀（6%）挤压中小企业预算；价格敏感度上升"

### 质量检查 / Quality Checks

- 具体到你的产品：不列通用政策——解释影响
- 可行动：能基于此洞察调整策略吗？
- 定期重评：宏观环境在变——不要静态分析

## 3.3 市场规模测算 / TAM/SAM/SOM Calculator

**触发词**：TAM、SAM、SOM、市场规模、市场测算、上探测算

**适用场景**：向投资人/高管提案（需要市场规模）；验证产品想法（市场够大吗？）；产品线优先级（哪个机会更大？）；设定增长目标（现实能捕获多少？）。不适用：内部工具（无外部市场）、定义问题之前（市场规模需要清晰问题空间）、作为唯一验证（配合客户研究）。

### 核心概念：三层市场规模模型 / Core Concept: Three-Layer Market-Size Model

**总可寻址市场（TAM）**：产品或服务的总市场需求。"如果我们捕获 100% 市场，营收是多少？"（最宽泛的市场，无约束）

**可服务市场（SAM）**：公司实际可瞄准的 TAM 细分。按地理、企业画像、人口统计或产品约束收窄。"我们实际能触达谁？"

**可获得市场（SOM）**：现实可捕获的 SAM 部分。考虑竞争、市场约束、进入市场能力。"未来 1-3 年我们能捕获什么？"

### 为什么有效 / Why It Works

- 自上而下验证：TAM → SAM → SOM 确保估算扎根现实
- 投资人友好：VC 和高管都理解的标准框架
- 引用支撑：真实数据源（统计局、Statista、世界银行）增加可信度
- 自适应：问题按情境调整（B2B vs B2C、美国 vs 全球等）

### 交互问题脚本（最多 4 个自适应问题）/ Interaction Question Script (up to 4 adaptive questions)

**问题 1：问题空间**——"基于已提供背景（或即将描述的），你要做市场规模测算的问题空间是什么？"

**问题 2：目标客户**——B2B 中小企业 vs 企业 vs B2C 大众 vs 小众；地理范围（国内 vs 全球）

**问题 3：变现模型**——订阅（年/月 ARPU）、一次性、交易抽成、广告

**问题 4：市场约束**——竞争强度、进入市场渠道、客户集中度

### 计算模板 / Calculation Template

```
TAM = 目标人口总数 × 人均年支出（ARPU）
SAM = TAM × 可服务比例（地理/画像/产品约束）
SOM = SAM × 可获得比例（竞争/进入市场能力，通常 1-3 年视角）
```

### 反模式 / Anti-Patterns

- 不是单一数字猜测："市场有 100 亿"无支撑数据
- 不是静态：市场在演变——每年重评
- 不是客户验证的替代品：市场规模 ≠ 产品-市场契合

## 3.4 获客渠道顾问 / Acquisition Channel Advisor

**触发词**：获客渠道、渠道评估、CAC、LTV、渠道规模/测试/放弃、市场预算分配

**适用场景**：评估是否规模化的新渠道（内容、付费、活动等）；跨渠道分配市场预算；评估是否砍掉表现不佳渠道；对比渠道优化 ROI；年度市场预算规划。不适用：全新渠道（<3 个月、<100 客户——数据不足）、测试渠道契合、战略渠道（如企业需直销团队与 CAC 无关）、无渠道级数据。

### 核心概念：渠道评估框架 / Core Concept: Channel Evaluation Framework

1. **单位经济**——获取成本和回报：
   - CAC（客户获取成本）、LTV（生命周期价值）、LTV:CAC 比、回本周期

2. **客户质量**——渠道客户是否留存和扩展：
   - 按渠道的分群留存率、流失率、NRR（净收入留存）、扩展率

3. **可扩展性**——渠道能否支撑所需量级：
   - 魔法数字（S&M 效率）、可寻址量（渠道 TAM）、饱和风险（边际递减）、CAC 趋势（上升/稳定/下降）

4. **战略契合**——渠道是否匹配进入市场战略：
   - 客户细分匹配（SMB vs 企业）、销售模式兼容（PLG vs 销售主导）、品牌定位对齐

### 决策矩阵 / Decision Matrix

| LTV:CAC | 回本周期 | 客户质量 | 可扩展性 | 决策 |
|---|---|---|---|---|
| >3:1 | <12 月 | 留存好 | 高量级 | **积极规模化** |
| 2-3:1 | 12-18 月 | 留存一般 | 中量级 | **测试与优化** |
| <2:1 | >18 月 | 留存差 | 低量级 | **砍掉或修复** |

### 交互问题脚本 / Interaction Question Script

**步骤 0：收集背景**——渠道名、使用时长（月）、月支出、月获客数、渠道 CAC、混合 CAC、混合 LTV、当前 MRR/ARR、目标增长率。可用估算值。

**步骤 1-4（自适应问题）**：
1. 单位经济：CAC、LTV、LTV:CAC、回本周期数据
2. 客户质量：渠道留存/流失、NRR、扩展率
3. 可扩展性：魔法数字、渠道可寻址量、CAC 趋势
4. 战略契合：客户细分匹配、销售模式、品牌对齐

**输出**：规模化/测试优化/砍掉修复决策 + 依据数据 + 建议行动。

### 反模式 / Anti-Patterns

- 不是虚荣指标："我们拿到 1 万注册！"30 天内流失就没意义
- 不是只看 CAC：低 CAC + 差留存比高 CAC + 好留存更糟
- 不忽略回本周期：5:1 LTV:CAC 配 36 个月回本周期是现金陷阱
- 不规模化损坏渠道：向低效渠道砸钱加速失败

## 3.5 逆向新闻稿 / Press Release

**触发词**：新闻稿、Working Backwards、亚马逊工作法、愿景定义、上线前验证

**适用场景**：定义新产品或重大功能；开发前对齐利益相关方愿景；测试产品想法是否吸引人；向高管提案或争取支持。不适用：琐碎功能、已建完产品（太晚了）、作为实际上线日新闻稿（这是规划文档，不是最终市场文案）。

### 核心概念：亚马逊 Working Backwards / Core Concept: Amazon Working Backwards

写任何代码之前，先从新闻稿和 FAQ 开始。新闻稿必须：
- 从客户视角撰写
- 聚焦解决的问题，而非构建的功能
- 简短（1-1.5 页）
- 有足够吸引力让客户想要产品

### 新闻稿结构 / Press Release Structure

1. **标题**：清晰、以收益为中心的发布公告
2. **日期行**：城市、州、日期
3. **导言段**：发布什么、面向谁、核心收益
4. **问题段**：产品解决的客户问题
5. **方案段**：产品如何解决问题（成果，非功能）
6. **公司领导人引语**：愿景、客户承诺
7. **补充细节**：支撑收益或数据
8. **公司介绍**：公司背景
9. **行动号召**：如何了解更多
10. **媒体联系**：新闻联系人

### 应用流程 / Application Flow

**步骤 1：收集背景**——产品/功能描述、目标客户/画像、问题陈述、核心收益、竞争背景、公司使命/价值观。缺背景先做发现。

**步骤 2：起草标题**——"[产品名] 由 [公司] 推出，旨在 [主要收益/目标]"
- ✅ "Acme Workflows 推出发票自动化，将小企业处理时间缩短 60%"
- ❌ "Acme 推出带 AI 功能的新产品"

**步骤 3：日期行与导言**——2-3 句以内；先点名客户问题，别急着说方案。

**步骤 4：解释问题**——具体问题（不是"低效"而是"手工发票处理每月 8 小时"）+ 数据/客户引语/研究验证问题真实。

**步骤 5：描述方案**——产品如何解决问题（成果表述）。

**步骤 6：领导人引语 + 补充细节 + 公司介绍 + 行动号召**。

### 质量检查 / Quality Checks

- 以客户为中心：不说规格——说客户成果
- 无内部行话：写给客户，不是工程师
- 具体："革命性提升生产力"是废话；"将报告生成时间从 8 小时减到 10 分钟"是真实的
- 诚实：不夸大产品实际能做的

## 3.6 产品停售沟通 / EOL Message

**触发词**：停售、EOL、产品下线、功能废弃、迁移沟通、日落公告

**适用场景**：停售产品/功能/服务；客户从旧平台迁移到新平台；收购目标的旧产品下线；废弃技术栈或 API。不适用：小功能调整（别过度沟通小改动）、还没有迁移计划（先知道如何支持客户再沟通）、希望客户没注意到（要透明）。

### 核心概念：EOL 消息框架 / Core Concept: The EOL Message Framework

有效的停售消息在改变诚实性与客户影响共情间取得平衡：
1. **公司背景**：你是谁，对客户的承诺
2. **公告**：停售什么，用什么替代
3. **理由**：为什么这个决定对客户有利（不只是对业务）
4. **当前产品背景**：产品是什么，服务了谁
5. **客户影响**：如何影响用户（承认干扰）
6. **迁移方案**：替代品是什么，比旧的强在哪
7. **支持措施**：如何帮助客户迁移
8. **时间线**：关键日期和里程碑
9. **行动号召**：下一步和联系方式

### 反模式 / Anti-Patterns

- 不是生硬的关闭通知："我们要停售产品 X 了。再见。"
- 不是业务中心：别用"这降低了我们的成本"开场
- 不模糊："很快"不是时间线
- 不防御：别怪客户（"低使用率迫使我们关闭"）

### 应用流程 / Application Flow

**步骤 1：收集背景**——停售对象、替代方案、时间线（公告/功能冻结/关停/数据导出截止）、客户影响（多少用户、哪些流程被打断）、支持计划（迁移支持、培训、折扣、数据导出工具）、理由（技术过时、战略转变、整合等）。缺背景别发消息——客户会问"我现在怎么办？"必须有答案。

**步骤 2：起草产品迁移叙事**
- **我们是谁**：[公司及与被停售产品的关系] + 对客户承诺 + 产品演进 + 未来愿景
- **公告**：[一句话明确陈述停售并介绍替代品]，例："我们将在 2026 年 12 月 31 日停售 Acme Workflows Classic，并将所有客户迁移到 Acme Workflows Pro"
- **理由（客户收益视角）**：因为：[技术进步/性能提升/更好匹配客户需求] → 对你意味着：[客户视角的影响和收益]
- **客户影响**：承认干扰："我们理解这会打乱你的工作流程……"
- **迁移方案**：替代品如何改进旧品
- **支持措施**：迁移工具、培训、时间线支持
- **时间线与行动号召**：清晰日期 + 下一步

## 3.7 公司情报研究 / Company Research

**触发词**：公司研究、竞品研究、高管访谈、公司画像、入职前研究、伙伴评估

**适用场景**：竞争分析（理解对手如何做 PM）；伙伴评估（评估文化契合与战略方向）；面试准备（理解公司文化与产品理念）；最佳实践标杆（向成功公司学习）；市场进入决策（理解在位者如何运作）。不适用：内部组织分析（这是外部研究）、无一手来源（高管未公开表态）、替代客户研究（这是公司视角，不是客户视角）。

### 核心概念：高管洞察框架 / Core Concept: Executive Insight Framework

跨多维度综合公司情报：
1. **公司概览**：基本信息、历史、行业背景
2. **高管引语**：CEO、COO、产品 VP、集团 PM 的战略愿景
3. **产品洞察**：战略、近期发布、创新重点
4. **转型战略**：数字化、AI、敏捷转型
5. **组织影响**：PM 如何影响战略、跨职能协作
6. **未来路线图**：即将推出的计划与预期挑战
7. **产品驱动增长（PLG）**：PLG 战略、数据驱动决策

### 应用流程 / Application Flow

**步骤 1：定义研究范围**——公司名、研究目的（如"理解支付平台产品战略用于竞争定位"）、关键问题（3 个：如"Stripe 如何看待平台可扩展性？""他们的开发者体验方法是什么？""他们如何排路线图 vs 企业定制请求？"）。

**步骤 2：收集公司概览**——基本信息（总部、行业、成立年份、规模、融资/估值）+ 关键里程碑历史。来源：公司网站（关于/新闻/博客）、LinkedIn、Crunchbase/PitchBook、维基百科。

**步骤 3：提取高管战略引语**——CEO/COO/产品 VP 近期引语 + 来源 + 日期 + 背景。来源：访谈、财报电话会议、博客文章、大会演讲、播客。

**步骤 4：产品策略分析**——近期发布、创新重点、产品哲学。

**步骤 5：转型战略分析**——数字化、AI、敏捷转型计划。

**步骤 6：组织影响分析**——PM 角色、跨职能协作、决策流程。

**步骤 7：未来路线图**——公开宣布的计划、行业预测、预期挑战。

### 反模式 / Anti-Patterns

- 不是财务分析：重点是产品战略，不是估值或股价
- 不是 SWOT：记录他们的视角，不是强弱评估
- 不是表面抓取：比"关于我们"页更深——找高管访谈、产品博客、财报记录

# 第四部分：数据与财务 / Part 4: Data & Finance

## 4.1 SaaS 财务指标速查表 / Finance Metrics Quickref

**触发词**：财务指标、指标公式、SaaS 指标速查、董事会准备、投资人沟通

**适用场景**：快速查公式或基准；准备董事会/投资人会议；评估决策时检查哪些指标重要；快速识别红旗。需要详细计算指导时配合 4.2/4.3 章节。

> 本技能合并自 finance-metrics-quickref、saas-revenue-growth-metrics、saas-economics-efficiency-metrics 三个高度重叠的指标文档，速查表与详解在此统一。

### 指标分类 / Metric Categories

四大家族：**收入与增长**（顶层收入）、**单位经济**（客户级盈利）、**资本效率**（现金管理）、**效率比率**（增长与盈利平衡）。

### 全指标速查表 / Full Metric Quick-Reference

| 指标 | 公式 | 衡量什么 | 良好基准 | 红旗 |
|---|---|---|---|---|
| 收入 | 费用前总销售额 | 顶层收入 | 增长率 >20% 年同比（按阶段） | 收入增长慢于成本 |
| ARPU | 总收入 / 总用户 | 单用户收入 | 因模式而异；跟踪趋势 | ARPU 逐群下降 |
| ARPA | MRR / 活跃账户 | 每账户收入 | SMB：$100-$1K；中端：$1K-$10K；企业：$10K+ | 高 ARPA + 低 ARPU（席位未变现） |
| ACV | 每合同年经常性收入 | 合同年化价值 | SMB：$5K-$25K；中端：$25K-$100K；企业：$100K+ | ACV 下降（无意下沉市场） |
| MRR/ARR | MRR × 12 = ARR | 可预测经常性收入 | 增长+质量重要；跟踪组成 | 新 MRR 下降而流失稳定/上升 |
| 流失率 | 流失客户 / 期初客户 | 取消客户比例 | 月 <2% 优秀，<5% 可接受；年 <10% 优秀 | 流失逐群上升 |
| NRR | (期初 ARR + 扩展 - 流失 - 收缩) / 期初 ARR × 100 | 收入留存+扩展 | >120% 优秀；100-120% 好；90-100% 可接受 | NRR <100%（基础在收缩） |
| 扩展收入 | 追加销售 + 交叉销售 + 用量增长 | 存量客户新增收入 | 占总收入 20-30% | 扩展 <10% MRR |
| Quick Ratio | (新 MRR + 扩展 MRR) / (流失 MRR + 收缩) | 收入得 vs 失 | >4 优秀；2-4 健康；<2 漏水桶 | Quick Ratio <2 |
| 毛利率 | (收入 - COGS) / 收入 × 100 | 直接成本后收入比例 | SaaS 70-85% 好；<60% 需关注 | 毛利率 <60% 或下降 |
| CAC | 总市场销售支出 / 新客户 | 获取一个客户成本 | 企业 $10K+ 可接受；SMB <$500 | CAC 上升而 LTV 持平 |
| LTV | ARPU × 毛利率% / 流失率 | 一个客户终身收入 | 必须 3x+ CAC；按细分不同 | LTV 逐群下降 |
| LTV:CAC | LTV / CAC | 单位经济效率 | 3:1 健康；<1:1 不可持续；>5:1 投资不足 | LTV:CAC <1.5:1 |
| 回本周期 | CAC / (月 ARPU × 毛利率%) | 回本所需月数 | <12 月优秀；12-18 可接受；>24 需关注 | 回本 >24 月（现金陷阱） |
| 贡献毛利 | (收入 - 全部可变成本) / 收入 × 100 | 可变成本后真实贡献 | SaaS 60-80% 好；<40% 需关注 | 贡献毛利 <40% |
| 烧钱率 | 月现金支出 - 收入 | 每月消耗现金 | 早期净烧 <$200K 可控；增长 <$500K | 净烧加速 |
| 跑道 | 现金余额 / 月净烧钱 | 资金耗尽月数 | 12+ 月好；6-12 可管理；<6 危机 | 跑道 <6 月 |
| OpEx | 市场销售 + 研发 + 管理 | 运营成本 | 应慢于收入增长 | OpEx 增长快于收入 |
| 净利润 | 收入 - 全部费用 | 实际盈亏 | 早期可为负；成熟 10-20%+ 利润率 | 无增长的亏损加速 |
| 40 法则 | 收入增长率% + 利润率% | 增长 vs 效率平衡 | >40 健康；25-40 可接受；<25 需关注 | 40 法则 <25 |
| 魔法数字 | (本季收入 - 上季收入) × 4 / 上季市场销售支出 | 市场销售效率 | >0.75 高效；0.5-0.75 可接受；<0.5 修 GTM | 魔法数字 <0.5 |
| 运营杠杆 | 收入增长 vs OpEx 增长 | 规模化效率 | 收入增长 > OpEx 增长 | OpEx 增长快于收入 |
| 总 vs 净收入 | 净 = 总 - 折扣 - 退款 - 抵免 | 实际保留收入 | 退款 <10%；折扣 <20% | 退款 >10%（产品问题） |
| 收入集中度 | 前 N 客户 / 总收入 | 大客户依赖 | 最大客户 <10%；前 10 <40% | 最大客户 >25%（存亡风险） |
| 收入组合 | 产品/细分收入 / 总收入 | 组合构成 | 无单品 >60% 为佳 | 单品 >80%（无多元化） |
| 分群分析 | 按加入日期分组追踪行为 | 业务是否变好 | 新群与旧群相同或更好 | 新群表现更差 |
| 增量性 | 行为造成的收入 - 基线 | 营销/促销真实影响 | 用对照组测试衡量 | 庆祝本就会发生的收入 |
| 营运资本 | 收入与回款间的现金时间差 | 现金 vs 收入时间 | 年预付 > 月账单 | 长账期拖垮跑道 |

### 快速决策框架 / Fast Decision Framework

**框架 1：该建这个功能吗？**
问：收入影响？（直接定价/附加 or 间接留存/转化）；毛利影响？（COGS 是否稀释毛利）；ROI？（收入影响 / 开发成本）
**建，如果**：首年 ROI >3x（直接变现），或 LTV 影响 >10x 开发成本（留存类），或战略价值压过短期 ROI
**不建，如果**：即使乐观采用也是负贡献毛利；回本周期超过客户平均生命周期
**检查指标**：收入、毛利率、LTV、贡献毛利

**框架 2：该规模化这个获客渠道吗？**
问：单位经济？（CAC、LTV、LTV:CAC）；现金效率？（回本周期）；客户质量？（分群留存、渠道 NRR）
**规模化，如果**：LTV:CAC >3 且回本 <12 月且留存好
**测试优化**：LTV:CAC 2-3，回本 12-18 月
**砍掉或修复**：LTV:CAC <2，回本 >18 月，留存差

**框架 3：公司健康吗？**
检查：增长（收入增长率、NRR）；单位经济（LTV:CAC、回本、毛利）；资本效率（40 法则、魔法数字、跑道）；战略位置（竞争护城河、收入集中度、运营杠杆）

## 4.2 业务健康诊断 / Business Health Diagnostic

**触发词**：业务健康、健康诊断、董事会准备、投资人汇报、单位经济检查

**适用场景**：全面了解 SaaS 业务健康（全维度）；识别哪些指标是红旗 vs 先行指标；准备董事会或投资人评审；融资前评估。

### 核心概念：业务健康框架 / Core Concept: Business Health Framework

SaaS 业务健康 = 四个维度协同工作：

1. **增长与留存**——在增长并留住客户吗？
   - 收入增长率、NRR、流失率、Quick Ratio

2. **单位经济**——商业模式在客户层面盈利吗？
   - CAC、LTV、LTV:CAC、回本周期、毛利率

3. **资本效率**——现金使用高效吗？
   - 烧钱率、跑道、40 法则、魔法数字

4. **战略位置**——为持续成功定位了吗？
   - 市场定位（低于/持平/高于市场价格）、竞争护城河（网络效应、数据、品牌）、收入集中风险、运营杠杆

### 分阶段基准 / Phase Benchmarks

**早期（ARR <$1000 万）**：
- 重点：产品-市场契合、单位经济
- 增长 >50% 年同比；LTV:CAC >3:1；毛利率 >70%；跑道 >12 个月
- 可接受：负利润率、高烧钱（如果单位经济成立）

**成长期（ARR $1000 万-$5000 万）**：
- 重点：高效规模化
- 增长 >40% 年同比；NRR >100%；40 法则 >40；魔法数字 >0.75
- 可接受：增长强劲时中等烧钱

**规模期（ARR $5000 万+）**：
- 重点：盈利能力、效率
- 增长 >25% 年同比；NRR >110%；40 法则 >40；利润率 >10%
- 要求：正或接近正的现金流

### 红旗分类 / Red-Flag Categories

**严重（立即修复）**：跑道 <6 个月；LTV:CAC <1.5:1；流失逐群加速；NRR <90%；魔法数字 <0.3

**高优先（本季度内修复）**：40 法则 <25；回本 >24 个月；Quick Ratio <2；毛利率 <60%；前 10 客户收入集中 >50%

**中优先（6 个月内处理）**：NRR 90-100%（持平不增长）；魔法数字 0.3-0.5；运营杠杆为负；流失率稳定但高（月 >5%）

### 反模式 / Anti-Patterns

- 不是单一指标："收入增长 50%，我们很好！"（忽略烧钱、流失、单位经济）
- 不分阶段：早期烧钱可接受；规模期烧钱是问题
- 不是静态：健康是方向性的——指标在改善还是恶化？
- 不只是数字：背景重要（竞争压力、市场变化、团队能力）

## 4.3 功能投资顾问 / Feature Investment Advisor

**触发词**：功能投资、建不建、功能 ROI、变现评估、投资回报

**适用场景**：在可量化收入/留存影响的功能间排优先级；评估昂贵功能（>1 工程师月）；建/买/合作决策；向利益相关方或领导层辩护功能优先级；选择直接变现（附加）vs 间接（留存）。不适用：基础功能（竞争对等必需）、纯定性影响（品牌、无量化留存的 UX 愉悦）、未验证问题（先做发现）、<1 周工作量（直接建）。

### 核心概念：功能投资框架 / Core Concept: Feature Investment Framework

1. **收入连接**——功能如何影响收入？
   - 直接变现（新层级、附加、用量计费）
   - 间接变现（留存、转化、扩展赋能）

2. **成本结构**——建设和运营成本？
   - 开发成本（一次性投资）
   - COGS 影响（持续基础设施、处理）
   - OpEx 影响（持续支持、维护）

3. **ROI 计算**——回报值不值得投资？
   - 直接变现：收入影响 / 开发成本
   - 留存功能：客户群 LTV 影响 / 开发成本
   - 计入毛利率，不只收入

4. **战略价值**——可能压过纯 ROI 的非财务价值
   - 竞争护城河（防止流失到竞品）
   - 平台赋能（解锁未来功能）
   - 市场定位（企业交易需要）
   - 风险降低（合规、安全）

### 交互问题脚本 / Interaction Question Script

**步骤 0：收集背景**——功能描述（1-2 句）、目标客户细分、当前 MRR/ARR（或预收入客户数）、当前 ARPU/ARPA、月流失率、毛利率%、开发成本估算（团队规模 × 时间）、持续 COGS/OpEx 影响。可用估算。

**问题 1：收入连接**——直接变现（新层级/附加/用量计费）vs 间接变现（留存/转化/扩展）vs 两者兼有

**问题 2：成本结构**——开发成本规模；COGS/OpEx 持续影响

**问题 3：ROI 视角**——直接 ROI、留存类 LTV 影响、战略价值权重

**问题 4：战略价值**——竞争护城河、平台赋能、市场定位、风险降低

**输出**：建/不建建议 + 支撑数学（ROI、回本、LTV 影响）+ 战略权衡说明。

### 反模式 / Anti-Patterns

- 不是单一功能评分：财务分析 + 战略判断结合
- 不是只看收入：考虑毛利、成本、ROI，不只顶层收入
- 不忽略留存：间接收入影响（流失降低）同样有效
- 不无验证建设：假设已做发现；这是财务视角

## 4.4 定价财务评估 / Finance-Based Pricing Advisor

**触发词**：定价评估、涨价、新层级、附加、折扣、定价 go/no-go

**适用场景**：评估具体定价变更的财务影响（如"该涨价 20% 吗？"）；量化收入、流失、转化权衡；在定价方案间做选择（测试 A vs B）；向领导层/董事会呈现定价影响。不适用：从零设计定价战略（用价值定价框架）、未验证支付意愿（先做客户研究）、无基线指标（ARPU、流失、转化率）、变更太小（<5% 价格变化，<10% 客户受影响）。

### 核心概念：定价影响框架 / Core Concept: Pricing Impact Framework

1. **收入影响**——如何改变 ARPU/ARPA？
   - 涨价直接收入提升；转化下降或流失增加的损失；净收入影响

2. **转化影响**——如何影响试用转付费或销售转化？
   - 高价可能降低转化率；更好打包可能提升转化；测试假设

3. **流失风险**——现有客户会因价格离开吗？
   - 老客户保护策略（grandfathering）；按细分的流失风险（SMB vs 企业）；流失弹性（客户对价格多敏感？）

4. **扩展影响**——创造还是阻塞扩展机会？
   - 新高级层级 = 追加路径；用量定价 = 客户增长带动扩展；附加 = 交叉销售机会

5. **CAC 回本影响**——定价变化影响单位经济吗？
   - 更高 ARPU = 更快回本；更低转化 = 更高有效 CAC；对 LTV:CAC 的净效应

### 定价变更类型 / Pricing Change Types

**直接变现变更**：涨价（全部客户或仅新客户）；新高级层级（创建追加路径）；付费附加（变现免费功能）；用量定价（按消费收费）

**折扣策略**：年付预付折扣（改善现金流）；批量折扣（更大交易）；促销定价（临时降价）

**打包变更**：功能捆绑（组合进层级）；解绑（拆成附加）；定价指标变更（席位 → 用量，反之）

### 交互问题脚本 / Interaction Question Script

**步骤 0：收集背景**——具体定价变更描述、当前 ARPU/ARPA、月流失率、转化率、毛利率、CAC、客户细分构成。

**问题 1：变更类型**——直接变现/折扣/打包

**问题 2：收入影响估算**——涨价幅度、受影响客户比例、预期净收入变化

**问题 3：流失与转化风险**——各细分的流失弹性、转化影响预期、老客户保护策略

**问题 4：回本与扩展影响**——对 CAC 回本、LTV:CAC、扩展路径的影响

**输出**：go/no-go 建议 + 财务模型（净收入变化、流失损益平衡点、回本影响）+ 风险缓解建议。

### 反模式 / Anti-Patterns

- 不是价值定价：评估提议变更，不是"该收多少钱？"
- 不是支付意愿研究：分析影响，不是"客户愿付多少？"
- 不是竞争定位：这是财务分析，不是市场定位
- 不是打包架构：评估一个变更，不是重设所有层级

## 4.5 PoL 探针 / Proof of Life Probe

**触发词**：PoL、验证探针、轻量验证、原型测试、先验证后开发、生存证明

**适用场景**：有具体可证伪假设要测试；特定风险阻塞下一个决策（技术可行性、用户任务完成、利益相关方支持）；几天内需要残酷真相；建设生产级软件为时过早或浪费；能在开始前说出"失败"长什么样。不适用：想打动高管（那是原型表演）；已知答案只求验证（那是确认偏差）；说不清假设或处置计划；学习目标太宽泛（"客户会喜欢吗？"）；用探针逃避硬决策。

### 核心概念 / Core Concepts

**生存证明（PoL）探针**是刻意的、一次性的验证实验，用最低成本最快回答一个具体问题。不是产品、不是 MVP、不是试点——是定向寻真任务。

起源：Dean Peters（Productside）提出，基于 Marty Cagan 2014 年原型风味研究和 Jeff Patton 的原则："**测试想法最贵的方式就是构建生产级软件。**"

### 5 个必备特征 / Five Must-Have Traits

| 特征 | 含义 | 为什么重要 |
|---|---|---|
| **轻量** | 最少资源投入（小时/天，非周） | 贵了你就舍不得在数据说话时杀死它 |
| **一次性** | 明确规划为删除，不是扩展 | 防止沉没成本谬误和范围蔓延 |
| **窄范围** | 只测一个具体假设或风险 | 宽泛实验产生模糊结果 |
| **残酷诚实** | 暴露严酷真相，不是虚荣指标 | 礼貌的数据是无用的数据 |
| **微小聚焦** | 侦察任务，绝非 MVP | 小表面积 = 更快学习循环 |

**反模式**：如果"原型"精致到舍不得删，就不是 PoL 探针——是原型表演。

### PoL 探针 vs MVP / PoL Probe vs MVP

| 维度 | PoL 探针 | MVP |
|---|---|---|
| 目的 | 通过窄假设测试降低决策风险 | 验证想法或捍卫路线图方向 |
| 范围 | 单一问题、单一风险 | 最小可发布产品增量 |
| 寿命 | 数小时到数天，然后删除 | 数周到数月，然后迭代 |
| 受众 | 内部团队 + 窄用户样本 | 生产环境的真实客户 |
| 保真度 | 刚好够捕捉信号的幻觉 | 生产级（或接近） |
| 结果 | 学到什么*不*管用 | 学到什么*管用*（并发布） |

**关键区分**：PoL 探针是 **MVP 之前的侦察**。跑探针决定是否该建 MVP，不是发布产品。

### 5 种原型风味 / Five Prototype Flavors

| 类型 | 核心问题 | 时间线 | 工具/方法 | 何时使用 |
|---|---|---|---|---|
| **1. 可行性检查** | "我们能建这个吗？" | 1-2 天 | GenAI 提示链、API 测试、数据完整性扫描、写完即删代码 | 技术风险未知；第三方依赖不明 |
| **2. 任务聚焦测试** | "用户能无摩擦完成任务吗？" | 2-5 天 | Optimal Workshop、UsabilityHub、任务流 | 关键时刻（字段标签、决策点、流失区）需验证 |
| **3. 叙事原型** | "这个工作流能赢得利益相关方支持吗？" | 1-3 天 | Loom 走查、Sora/Synthesia 视频、幻灯片故事板 | 需要"讲述 vs 测试"——分享故事、衡量兴趣 |
| **4. 合成数据模拟** | "能无生产风险建模吗？" | 2-4 天 | Synthea（用户模拟）、LangFlow（提示逻辑测试） | 边界案例探索；未知之未知暴露 |
| **5. 氛围编程探针** | "方案能经受真实用户接触吗？" | 2-3 天 | 画布+低代码+表格组合 = "科学怪人软件" | 需要工作流/UX 用户反馈，但不需要生产级代码 |

**黄金法则**："*用最便宜的原型讲最残酷的真相。如果不刺痛，大概只是表演。*"

### PoL 探针模板 / PoL Probe Template

```markdown

[一句话陈述你所相信的]

## 原型类型 / Prototype Types
[从 5 种风味选一]

[如何运行：参与者、场景、成功标准]

## 成功 / 失败标准 / Success / Failure Criteria
[预先定义：什么算验证，什么算证伪]

## 处置计划 / Disposal Plan
[何时删除、数据保留什么、学到的经验如何记录]
```

# 第五部分：日常工作 / Part 5: Day-to-Day Work

## 5.1 点子验证器 / Idea Validator

**触发词**：验证这个想法、这个点子怎么样、值得做吗、创意评估

**适用场景**：任何新产品想法、功能想法或业务创意在投入资源前的快速评估；筛选创意积压；给创业者/PM 提供结构化的想法体检。

### 核心概念：五维评分框架 / Core Concept: Five-Dimension Scoring Framework

对每个维度用 强 / 中 / 弱 评级：

**1. 问题严重性**——问题有多大？
- 强：高频率 + 高痛苦 + 无满意替代方案
- 中：中频率 + 中痛苦
- 弱：低频率或低痛苦

**2. 市场证据**——有市场需求证据吗？
- 强：现有付费客户、搜索趋势上升、社区热议
- 中：间接信号（相关产品成功、用户抱怨）
- 弱：纯推测

**3. 方案差异化**——你的方案独特在哪？
- 强：10 倍改进或全新品类
- 中：2-3 倍改进
- 弱：Me-too 复制

**4. 可行性**——技术上能建吗？
- 强：团队已有能力
- 中：需要学习或外包
- 弱：能力完全缺失

**5. 商业可行性**——能赚钱吗？
- 强：清晰变现路径 + 良好单位经济
- 中：变现路径模糊
- 弱：无变现路径

### 快速竞品扫描 / Quick Competitive Scan

| 竞品/替代 | 他们做什么 | 他们不做什么 | 用户抱怨什么 |
|---|---|---|---|
| [竞品 1] | | | |
| [竞品 2] | | | |
| [非竞争替代] | | | |

### 判决规则 / Verdict Rules

- **GO（去做）**：≥4 个强，无弱
- **ITERATE（迭代）**：2-3 个强，有清晰改进路径
- **STOP（停止）**：≤1 个强，或有致命弱项

### 杀手问题（任一为"是"则重新考虑）/ Killer Questions (reconsider if any is "yes")

1. 创始人/团队本身是目标用户吗？（有天然同理心但需验证外部需求）
2. 市场上有类似产品失败了吗？为什么？
3. 你能说出 10 个潜在客户的名字吗？
4. 如果今天上线，第一批用户会是谁？

### 实验建议 / Experiment Suggestions

验证器输出后，用 4.5 PoL 探针设计最小验证实验（访谈 5-10 人、落地页测试、原型测试）。

## 5.2 产品设计评审 / Product Designer

**触发词**：产品评审、设计评审、UX 检查、界面反馈、体验优化

**适用场景**：发布前评审产品界面/流程；用结构化框架给设计师反馈；检查 AI 产品特有体验问题；按屏幕类型（表单、表格、引导流程、设置、弹窗）逐项检查。

### 核心概念：六维评审框架 / Core Concept: Six-Dimension Review Framework

| 维度 | 检查什么 | 常见问题 |
|---|---|---|
| **清晰度** | 用户理解页面在说什么吗？ | 行业术语、模糊按钮文案、无价值主张 |
| **流程** | 完成任务顺畅吗？ | 多余步骤、死胡同、无进度反馈 |
| **信息架构** | 信息组织合理吗？ | 相关项分散、层级混乱、无搜索 |
| **一致性** | 交互模式统一吗？ | 同类操作不同样式、术语不一 |
| **错误处理** | 出错时有帮助吗？ | 无错误提示、提示不明确、数据丢失 |
| **无障碍** | 所有用户可用吗？ | 对比度不足、无键盘导航、无 alt 文本 |

### 三级反馈规则 / Three-Level Feedback Rules

- **必须修复（Must Fix）**：阻断任务完成、数据丢失、完全困惑
- **应该修复（Should Fix）**：显著摩擦、一致性破坏
- **考虑改进（Consider）**：体验优化、锦上添花

### AI 产品特有评审点 / AI-Product-Specific Review Points

- **幻觉风险**：AI 输出错误时有兜底/标注吗？
- **不确定性沟通**：AI 不确定时如何表达？
- **控制感**：用户能否撤销/调整 AI 行为？
- **加载体验**：长生成时间有进度反馈吗？
- **提示词可见性**：用户知道 AI 基于什么回答吗？

### 按屏幕类型检查清单 / Check List by Screen Type

**表单**：
- 必填项标注清晰？错误定位到具体字段？提交后反馈明确？
- 长表单有分组和进度？移动端输入类型正确（数字键盘等）？

**表格**：
- 列可排序/筛选？空状态有引导？大数据量有分页/虚拟滚动？
- 关键操作（编辑/删除）可达且可撤销？

**引导流程**：
- 步骤有进度指示？可跳过？返回不丢失数据？
- 每步只有一个主 CTA？价值主张在第一步讲清？

**设置页**：
- 分组清晰（通用/安全/通知）？危险操作有确认？
- 变更即时生效还是需保存？有说明文字？

**弹窗**：
- 有明确关闭路径（X、ESC、点击遮罩）？有标题和焦点管理？
- 不阻塞关键流程？小屏适配？

### 反馈输出格式 / Feedback Output Format

```
## 评审结果：[页面/流程名]

### 必须修复 / Must Fix
1. [问题] — 位置：[具体元素] — 原因：[影响]
### 应该修复 / Should Fix
1. [问题] — 建议：[修复方向]
### 考虑改进 / Consider Improving
1. [问题] — 建议：[修复方向]
```

## 5.3 提示词工程师 / Prompt Engineer

**触发词**：提示词、prompt、AI 输出不好、优化提示、提示词调试

**适用场景**：设计生产级提示词；AI 输出不理想时系统性调试；为团队沉淀提示词规范；评估提示词质量。

### 核心概念：七维诊断表 / Core Concept: Seven-Dimension Diagnostic Table

| 维度 | 检查 | 改进方向 |
|---|---|---|
| **角色** | 有明确角色设定吗？ | 指定角色 + 知识背景 + 视角 |
| **上下文** | AI 知道足够背景吗？ | 补充任务背景、数据、约束 |
| **指令** | 指令清晰无歧义吗？ | 拆分步骤、用动词开头、明确禁止项 |
| **输出格式** | 格式有约束吗？ | 指定结构（JSON、表格、清单）、长度 |
| **示例** | 有 Few-shot 示例吗？ | 2-3 个高质量正例 + 反例 |
| **约束** | 有边界条件吗？ | 长度、语气、受众、排除项 |
| **评估** | 如何验证输出质量？ | 定义评估标准、自检清单 |

### 七种核心技术 / Seven Core Techniques

1. **角色设定（Role Priming）**：开头设定专家角色
2. **结构化输出（Structured Output）**：要求 JSON/表格/固定模板
3. **思维链（Chain of Thought）**：让 AI 分步思考再回答
4. **少样本示例（Few-Shot）**：提供范例校准风格与格式
5. **约束声明（Constraints）**：明确边界与禁止行为
6. **评估循环（Evaluation）**：要求自检或与标准对比
7. **分隔符（Delimiters）**：用符号区隔指令与输入，防注入

### 提示词调试表（症状-原因-修复）/ Prompt Debugging Table (Symptom–Cause–Fix)

| 症状 | 原因 | 修复 |
|---|---|---|
| 输出泛泛而谈 | 无角色/无示例 | 加角色 + Few-shot 示例 |
| 输出偏离主题 | 上下文不足 | 补充背景与目标 |
| 格式混乱 | 无格式约束 | 指定输出结构 |
| 编造事实 | 无约束 + 无验证 | 要求标注不确定 + 给数据源 |
| 语气不对 | 未指定受众 | 明确受众与语气 |
| 输出过长/过短 | 无长度约束 | 给字数/段落范围 |

### 前后对比示例 / Before/After Examples

**差提示**："帮我写个产品文案"
**好提示**："你是一位 B2B SaaS 增长文案专家。为我们的项目管理工具写 50 字以内的落地页副标题，面向 100 人以上公司的工程总监，突出'减少跨团队沟通成本'，语气专业但不冰冷。避免空洞词汇如'创新''赋能'。格式：仅输出 3 个候选，编号列出。"

## 5.4 状态更新撰写 / Status Update Writer

**触发词**：写周报、状态更新、进展汇报、TL;DR、同步信息

**适用场景**：撰写周/月/季度状态更新；向不同层级受众（CEO、VP、跨职能、董事会）调整信息；QBR 汇报准备。

### 核心概念：TL;DR 结构 / Core Concept: TL;DR Structure

```
## TL;DR（1-2 句，最高层结论）/ TL;DR (1–2 sentences, top-level takeaway)
## 状态（On Track / At Risk / Blocked + 原因）/ Status (On Track / At Risk / Blocked + reason)
## 进展（本周/本周期完成的关键事项）/ Progress (key items completed this week/cycle)
## 下一步（下周/下周期计划）/ Next (planned for next week/cycle)
## 风险（需要关注的阻塞与缓解）/ Risks (blockers to watch & mitigations)
## 决策（需要谁做什么决定）/ Decisions (who needs to decide what)
## 指标（关键数字变化，附解释）/ Metrics (key number changes, with context)
```

### 受众校准表 / Audience Calibration Table

| 受众 | 关注点 | 信息深度 | 篇幅 |
|---|---|---|---|
| CEO | 目标达成、风险、决策 | 高层级 + 关键指标 | 5-10 行 |
| VP | 进展 vs 计划、依赖、团队健康 | 中层 + 关键指标 | 半页 |
| 跨职能伙伴 | 接口、依赖、时间线 | 与他们相关的细节 | 半页 |
| 工程负责人 | 技术风险、范围变化、协作 | 技术细节 | 一页 |
| 跳级领导 | 成果、成长、障碍 | 成果导向 | 5-10 行 |
| 董事会 | 战略进展、指标、资本 | 战略 + 数据 | 一页 |

### 节奏适配 / Rhythm Adaptation

- **每日**：阻塞、决策请求、时间敏感风险（极简）
- **每周**：TL;DR + 进展 + 下一步 + 风险
- **每月**：+ 指标趋势 + 上月复盘
- **季度（QBR）**：+ 目标 vs 结果 + 战略调整 + 下季度计划

### 写作规则 / Writing Rules

1. 结论先行：最重要的信息第一行
2. 状态明确：不要用"还行"——用 On Track / At Risk / Blocked + 原因
3. 量化进展："完成 3/5 个里程碑"而非"进展顺利"
4. 风险带缓解：每个风险至少一个应对方案
5. 决策明确化："需要 [谁] 在 [何时] 前决定 [什么]"
6. 指标带解释：数字变化 + 为什么变化 + 意味着什么
7. 无惊喜原则：坏消息尽早、直接、带计划

## 5.5 LinkedIn 帖子撰写 / LinkedIn Post Writer

**触发词**：LinkedIn 文案、发帖、个人品牌、职场内容、钩子

**适用场景**：撰写高参与度 LinkedIn 帖子；建立个人专业品牌；分享产品洞察；招聘/活动预热。

### 核心概念：钩子公式 / Core Concept: Hook Formula

首行决定 80% 的打开率。七种高表现钩子：

1. **大胆断言**："大多数产品经理都在浪费 60% 的时间"
2. **具体结果**："我用了 3 个框架把流失率降了 40%"
3. **反直觉观点**："优先级排序是伪命题"
4. **好奇缺口**："我错了。这 5 年我一直在用错误的指标"
5. **共鸣痛点**："周五 5 点改需求，懂的都懂"
6. **转型故事**："从被裁员到拿到 3 个 offer，我做了这 5 件事"
7. **互动提问**："你的团队每周花多少小时在无效会议上？"

### 结构与再钩子（Re-hook）/ Structure & Re-hook

```
[钩子第一行]

[故事/背景 2-4 行]——建立情境

[核心内容 3-5 点]——可操作价值

[再钩子]——每 3-5 行插入小钩子（转折、数字、提问）保持阅读

[行动号召]——互动提问或引导评论
```

### 黄金规则 / Golden Rules

- **800-1300 字符**：LinkedIn 最佳长度范围
- **写给一个人**："写给你认识的一个具体的人"，比"写给所有人"有力 10 倍
- **每段 ≤3 行**：移动端阅读，长段落直接划走
- **一次一个观点**：一条帖子只讲一件事
- **数字具体化**："提升 40%"胜过"大幅提升"
- **自曝其短**：承认失败/纠错的内容互动率最高
- **第一人称经验**：不说教，讲经历

### 发布前检查清单 / Pre-Publish Checklist

- [ ] 第一行有钩子吗？
- [ ] 前 3 行内有实质内容吗？
- [ ] 每段 ≤3 行吗？
- [ ] 有具体数字/例子吗？
- [ ] 结尾有明确行动号召吗？
- [ ] 对目标读者有价值吗？（不是自我表扬）
- [ ] 800-1300 字符吗？

# 第六部分：用户研究 / Part 6: User Research

## 6.1 客户旅程地图 / Customer Journey Map

**触发词**：旅程地图、客户旅程、触点分析、journey map、体验地图

**适用场景**：理解客户全生命周期体验；识别关键时刻（moment of truth）与痛点；跨职能对齐客户视角；设计改进优先级。不适用：单次交互的战术问题（用任务分析）、内部流程优化（旅程地图是客户视角）、没有客户洞察就虚构地图。

> 本技能合并自 customer-journey-map（框架方法）与 customer-journey-mapping-workshop（交互式工作坊），二者共用 NNGroup 框架。

### 核心概念：NNGroup 旅程地图框架 / Core Concept: NNGroup Journey Map Framework

**五阶段 × 六维度矩阵**：

| 阶段 | 描述 |
|---|---|
| 认知（Awareness） | 发现产品/品牌存在 |
| 考虑（Consideration） | 评估是否适合 |
| 决策（Decision） | 选择购买 |
| 服务（Service） | 使用产品/接受服务 |
| 忠诚（Loyalty） | 复购、推荐、留存 |

**六维度**（每个阶段都要填写）：
1. **行动**：用户在该阶段做什么
2. **触点**：与产品/品牌的交互点
3. **体验**：情感体验（正面/负面）
4. **KPI**：该阶段的关键指标
5. **业务目标**：该阶段对业务的意义
6. **参与团队**：负责该阶段/触点的内部团队

### 工作坊五要素 / Five Workshop Elements

NNGroup 定义旅程地图必需的五要素：
1. **主角（Actor）**——旅程的主人公（真实画像，非抽象用户）
2. **场景（Scenario）**——地图覆盖的情境（具体目标导向）
3. **阶段（Phases）**——旅程的高层阶段划分
4. **行动与情感（Actions & Emotions）**——每阶段做什么、感受如何
5. **机会（Opportunities）**——地图揭示的改进机会

### 应用流程（7 步）/ Application Flow (7 steps)

1. **确定主角与场景**：选择画像 + 具体情境（如"首次使用产品完成设置"）
2. **收集数据**：访谈、分析数据、支持工单、调查（基于真实洞察，不凭假设）
3. **绘制阶段**：从认知到忠诚（或项目相关阶段）
4. **填充行动与触点**：每阶段的用户行为与交互点
5. **标注情感曲线**：记录体验高低点（关键时刻）
6. **添加 KPI 与业务目标**：连接每阶段业务价值
7. **识别机会**：输出机会列表并按影响/投入排序

### 交互工作坊问题脚本（5 个自适应问题）/ Interactive Workshop Question Script (5 adaptive questions)

**问题 1：主角是谁？**
"我们要绘制谁的用户旅程？"
1. **现有客户**——已在使用产品的典型用户
2. **潜在客户**——考虑购买但未转化的用户
3. **新用户**——刚注册/首次使用
4. **流失用户**——已离开的用户（理解为什么）

**问题 2：场景是什么？**
"旅程覆盖什么具体情境？"（如"首次设置"、"升级付费"、"遇到问题寻求帮助"）

**问题 3：阶段如何划分？**——确认旅程的阶段边界

**问题 4：关键触点有哪些？**——用户与产品的交互点清单

**问题 5：最大的痛点/机会在哪？**——识别情感低谷与改进机会

### 输出模板 / Output Template

```markdown
# 客户旅程地图：[主角] × [场景] / Customer Journey Map: [persona] × [scenario]

## 主角 / Persona
[名称、角色、背景、目标、痛点]
```

## 6.2 发现访谈准备 / Discovery Interview Prep

**触发词**：访谈准备、用户访谈、研究计划、访谈提纲、Mom Test

**适用场景**：计划客户访谈前设计研究方案；确保访谈能获取真实行为而非礼貌意见；标准化访谈流程；团队多人访谈的一致性。

### 核心概念 / Core Concepts

好的访谈准备 = 研究目标 × 细分人群 × 约束条件 × 方法学。输出一份可直接执行的访谈计划，包含开场、核心问题（Mom Test 风格）、收尾、偏见清单与成功标准。

### 交互问题脚本（4 个自适应问题）/ Interaction Question Script (4 adaptive questions)

**问题 1：研究目标**
"你希望通过访谈回答什么问题？"
1. **验证问题**——确认痛点真实存在且足够严重
2. **理解行为**——了解用户当前如何完成某任务
3. **测试方案**——评估方案概念/原型的反应
4. **探索发现**——开放式理解某领域

**问题 2：目标细分**
"访谈谁？"
1. **现有客户**——最易触达，但可能有"现状偏差"
2. **流失用户**——最诚实的反馈来源
3. **潜在客户**——验证新市场假设
4. **多细分混合**——对比不同群体

**问题 3：约束条件**
"有什么限制？"（时间、预算、地域、样本量、招募渠道）

**问题 4：方法学**
"用什么访谈方式？"
1. **结构化**——固定问题清单（可比较、少深度）
2. **半结构化**——核心问题 + 自由追问（推荐）
3. **非结构化**——只定主题（深度高、难比较）

### 访谈计划模板 / Interview Plan Template

```markdown
# 访谈计划 / Interview Plan

## 研究目标 / Research Goals
[要回答的核心问题]

## 参与者 / Participants
- 人数：[5-8 人为宜]
- 细分：[描述]
- 招募渠道：[如何找到]

## 开场（5 分钟）/ Opening (5 min)
- 自我介绍 + 研究目的说明
- 告知记录方式 + 征求同意
- "没有对错答案，请基于真实经历回答"

## 核心问题（Mom Test 风格，30 分钟）/ Core Questions (Mom Test style, 30 min)
**行为导向**（过去时，不假设）：
1. "上次你遇到 [问题] 是什么时候？带我走一遍"
2. "你现在怎么解决这个问题？用什么工具/方法？"
3. "这个方案让你花了多少时间/钱？"
4. "你试过哪些其他方案？为什么放弃？"

**避免问题**（会得到谎言）：
- ❌ "如果有一个 [功能]，你会用吗？"（假设性问题）
- ❌ "你觉得这个想法怎么样？"（寻求表扬）
- ❌ "你会为此付费吗？"（礼貌性同意）

## 收尾（5 分钟）/ Wrap-up (5 min)
- "还有什么我应该了解的吗？"
- "你能推荐 2-3 个有类似经历的人吗？"（滚雪球招募）
- 感谢 + 后续安排

## 偏见清单（访谈中自检）/ Bias Checklist (self-check during interviews)
- 引导性问题（"是不是很烦？"）
- 认可性点头（诱导用户说你想听的）
- 为自己的方案辩护
- 只记录支持假设的证据

## 成功标准 / Success Criteria
- 完成 N 场访谈
- 每场至少 2 个具体行为故事
- 发现 X 个模式/主题
```

### 常见陷阱 / Common Pitfalls

- 问"会不会用"而非"怎么用"（假设性问题引发礼貌谎言）
- 讲产品太多（访谈是了解用户，不是推销）
- 样本太少或太单一
- 无记录（凭记忆会严重失真）
- 访谈后无综合流程（洞察烂在笔记里）

## 6.3 Discovery 流程 / Discovery Process

**触发词**：发现流程、discovery、需求探索、持续发现、研究规划

**适用场景**：启动系统化的客户发现项目；从问题定义到决策记录的全流程；编排多个研究技能的组合使用；建立团队持续发现习惯。

### 核心概念 / Core Concepts

发现不是一次性访谈，是 2-4 周的持续流程：定义问题 → 规划研究 → 开展研究 → 综合洞察 → 生成验证方案 → 决策记录。与持续发现（Teresa Torres）理念一致：把发现建成习惯而非项目。

### 六阶段流程（2-4 周）/ Six-Phase Process (2–4 weeks)

**阶段 1：定义问题（第 1 周，1-2 天）**
- 明确要探索的业务问题/决策
- 用问题框架画布（见 7.3）框定
- 输出：清晰的探索范围 + 成功标准
- **决策点 1**：问题够具体吗？→ 否：继续框定；是：进入规划

**阶段 2：研究规划（第 1 周，3-4 天）**
- 设计访谈计划（见 6.2）
- 定义细分人群与招募渠道
- 准备研究工具（访谈提纲、观察清单）
- 输出：研究计划 + 时间表

**阶段 3：开展研究（第 1-2 周）**
- 执行访谈（5-10 场，分散安排）
- 补充研究：可用性测试、数据分析、调查
- 每场访谈后 24 小时内记录洞察
- 输出：访谈记录 + 原始洞察

**阶段 4：综合洞察（第 2 周，1-2 天）**
- 亲和图：聚类原始洞察为主题
- 绘制旅程地图（见 6.1）定位痛点
- 更新 JTBD 陈述（见 1.4）
- 输出：洞察主题 + 机会清单
- **决策点 2**：有足够证据支持方向吗？→ 否：补充研究；是：进入方案

**阶段 5：生成验证方案（第 2-3 周）**
- 用机会-解决方案树（见 2.2）映射方案
- 为每个方案定义假设（见 2.4 Epic 假设）
- 设计 PoL 探针（见 4.5）轻量验证
- 输出：候选方案 + 验证实验

**阶段 6：决策记录（第 3-4 周）**
- 记录关键决策、依据与证据
- 更新路线图（见 2.6）
- 沉淀"学到了什么"文档
- **决策点 3**：继续探索还是进入交付？→ 输出最终建议

### 编排技能组合 / Orchestrating Skill Combinations

| 阶段 | 使用技能 | 类型 |
|---|---|---|
| 定义问题 | 问题框架画布、问题陈述 | 交互/组件 |
| 规划 | 访谈准备 | 交互 |
| 开展研究 | 访谈准备、JTBD 工作台 | 交互/组件 |
| 综合 | 旅程地图、JTBD | 组件/工作坊 |
| 方案 | 机会树、Epic 假设、PoL 探针 | 交互/组件/组件 |
| 决策 | 路线图规划 | 工作流 |

### 常见陷阱 / Common Pitfalls

- 跳过定义直接访谈（浪费的访谈源于模糊的问题）
- 访谈量 > 综合量（洞察价值在综合不在数量）
- 研究完美主义（迭代优于完美，2-4 周够了）
- 无决策记录（发现成果随会议消散）
- 发现与交付脱节（方案不进路线图等于没发现）

## 6.4 Proto Persona（假设驱动画像）/ Hypothesis-Driven Persona

**触发词**：人物画像、persona、假设画像、原型画像、目标用户定义

**适用场景**：项目早期快速定义目标用户假设；没有资源做完整人物研究时的替代；为访谈招募提供筛选标准；团队对齐"我们在为谁做产品"。

### 核心概念 / Core Concepts

Proto Persona 是基于现有知识与假设构建的轻量画像——不是研究产物，是**假设声明**，必须通过后续研究验证或推翻。它让假设显性化，避免团队各自脑补不同的"用户"。

### Proto vs 验证画像 / Proto vs Validation Persona

| 维度 | Proto Persona | 验证画像 |
|---|---|---|
| 来源 | 假设、轶事、领域知识 | 访谈、数据、观察 |
| 时间 | 项目早期（数小时） | 研究后（数周） |
| 置信度 | 低——待验证 | 高——有证据 |
| 用途 | 对齐假设、指导招募 | 设计决策、优先级 |
| 更新 | 快速迭代 | 定期回顾 |

### 画像模板 / Persona Template

```markdown
# [画像名称]（Proto Persona）/ [Persona Name] (Proto Persona)

## 一句话简介 / One-Line Intro
[角色 + 情境 + 核心痛点]

## 背景与人口统计 / Background & Demographics
- 角色/职位：[如"小企业主"、"工程总监"]
- 公司规模：[如"10-50 人"]
- 关键特征：[2-3 个显著特征]

## 代表语录 / Representative Quotes
"[一句代表他们心态的话]"

## 痛点（Pains）/ Pains
- [痛点 1：频率 + 强度]
- [痛点 2]
- [痛点 3]

## 目标（Gains/Goals）/ Gains / Goals
- [目标 1]
- [目标 2]

## 影响力与决策权 / Influence & Decision Power
- 决策角色：[购买者/使用者/影响者/审批者]
- 预算影响：[高/中/低]
- 技术成熟度：[如"技术友好"、"需要保姆式支持"]

## 假设清单（必须验证）/ Assumption List (must validate)
- [ ] 假设 1：[如何验证]
- [ ] 假设 2：[如何验证]
```

### 应用流程 / Application Flow

1. **收集现有知识**：团队头脑风暴已知的用户信息
2. **创建 1-3 个画像**：聚焦最重要的细分（贪多嚼不烂）
3. **标注假设**：明确区分"已知"与"猜测"
4. **用于招募筛选**：画像特征 → 访谈招募标准
5. **验证与更新**：访谈后修正画像，移除证伪的假设

### 常见陷阱 / Common Pitfalls

- 画像过多（超过 3 个 = 没有重点）
- 把假设当事实（必须标注"假设"并验证）
- 虚构细节（如确切的年龄分布——除非有依据）
- 画像与决策脱节（每次设计决策都回看画像）

# 第七部分：需求与文档 / Part 7: Requirements & Documentation

## 7.1 精益 UX 画布 / Lean UX Canvas

**触发词**：精益画布、Lean UX、业务问题、假设验证、最小实验

**适用场景**：新产品/功能启动时对齐假设；把模糊想法结构化；以业务成果为导向定义用户成果；设计最小实验验证风险假设。不适用：需求已完全明确（直接写 PRD）、无业务问题定义（先框定问题）、作为一次性文档（画布是活文档）。

### 核心概念：八格画布（Jeff Gothelf Lean UX Canvas v2）/ Core Concept: Eight-Box Canvas (Jeff Gothelf Lean UX Canvas v2)

1. **业务问题**：我们要解决什么业务问题？影响谁？多大？
2. **业务成果**：解决后的可衡量结果是什么？
3. **用户**：目标用户是谁？（见 6.4 Proto Persona）
4. **用户成果**：用户达成什么才算成功？
5. **解决方案**：我们计划构建什么？（多种可能）
6. **假设**：哪些假设必须为真方案才有效？
7. **最需学习**：最关键的一个未知是什么？
8. **最小实验**：验证最关键假设的最便宜实验？

### 画布模板 / Canvas Template

```markdown
# Lean UX 画布：[产品/功能名] / Lean UX Canvas: [product/feature]

## 1. 业务问题 / 1. Business Problem
[问题 + 影响谁 + 规模]
例："中小企业每月在发票处理上浪费 8 小时，导致现金流管理滞后"

## 2. 业务成果 / 2. Business Outcome
[可衡量结果]
例："发票处理时间减少 50%，回款周期缩短 30%"

## 3. 用户 / 3. Users
[画像 + 特征]
例："Sarah，自由设计师，10+ 客户，无财务人员"

## 4. 用户成果 / 4. User Outcomes
[用户角度成功]
例："每月花在发票上的时间从 8 小时减到 1 小时"

## 5. 解决方案 / 5. Solution
[方案 A/B/C]
例："A：自动提醒工具；B：发票模板库；C：会计集成"

## 6. 假设 / 6. Assumptions
[必须为真的假设清单]
例："1. 用户愿意自动化财务流程；2. 提醒不显得冒犯……"

## 7. 最需学习 / 7. What Must Be Learned
[最关键未知]
例："用户会信任 AI 自动发送付款提醒吗？"

## 8. 最小实验 / 8. Minimal Experiment
[最便宜验证]
例："5 个用户的绿野仙踪测试 + 访谈"
```

### 风险四分类 / Four Risk Categories

- **价值风险**：用户真的需要吗？
- **可用性风险**：用户会用吗？
- **可行性风险**：我们能建吗？
- **商业性风险**：能盈利吗？

优先验证价值风险（最致命）。用 PoL 探针（见 4.5）设计实验。

### 交互问题脚本（8 个自适应问题，逐格填充）/ Interaction Question Script (8 adaptive questions, box by box)

**问题 1**："我们要解决什么业务问题？"→ 业务问题
**问题 2**："解决后业务上可衡量的成功是什么？"→ 业务成果
**问题 3**："谁受此问题影响？"→ 用户（选项：现有客户/潜在客户/流失客户/内部用户）
**问题 4**："用户达成什么才算成功？"→ 用户成果
**问题 5**："我们计划构建什么？"→ 解决方案（鼓励发散多个选项）
**问题 6**："哪些假设必须为真？"→ 假设清单
**问题 7**："最需学习的一个未知是什么？"→ 关键未知
**问题 8**："验证它最便宜的实验是什么？"→ 最小实验

### 常见陷阱 / Common Pitfalls

- 解决方案优先（先填方案，问题后补——顺序错了）
- 假设与事实混淆（假设需标注并验证）
- 最需学习不聚焦（"最"只能有一个）
- 实验设计过重（最小实验应小时级，非周级）

## 7.2 PRD 开发 / PRD Development

**触发词**：PRD、产品需求文档、需求文档、功能规格、PRD 模板

**适用场景**：撰写新产品/功能 PRD；PRD 评审前自检；从发现到需求的转化；跨职能对齐需求。不适用：问题未验证（先做发现）、琐碎变更（直接描述）、把 PRD 当路线图（PRD 是交付文档，路线图是策略文档）。

### 核心概念：PRD 十节结构 / Core Concept: Ten-Section PRD Structure

1. **执行摘要**：一页内讲清"做什么、为什么、成功长什么样"
2. **问题陈述**：用户问题（用 7.4 问题陈述框架）
3. **目标用户**：画像 + 优先级
4. **战略背景**：如何连接公司/产品战略
5. **方案概述**：解决方案高层描述（非详细规格）
6. **成功指标**：主指标、次指标、护栏指标
7. **用户故事**：核心场景（用 7.5 用户故事格式）
8. **范围外**：明确不做什么
9. **依赖与风险**：技术、组织、时间线依赖
10. **开放问题**：待决策事项清单

### 三类指标 / Three Metric Types

- **主指标（North Star）**：方案要直接驱动的指标
- **次指标**：支撑主指标的分解指标
- **护栏指标**：不可被牺牲的指标（如性能、可用性、收入）

### 八阶段开发流程（2-4 天）/ Eight-Phase Development Flow (2–4 days)

**阶段 1：收集背景（2-4 小时）**
- 发现洞察（访谈、数据、支持工单）
- 战略背景（OKR、路线图）
- 技术约束与机会

**阶段 2：定义问题（2-4 小时）**
- 用问题框架画布（见 7.3）框定
- 撰写问题陈述（见 7.4）
- **质量门 1**：问题是否被验证？（利益相关方 + 用户证据）

**阶段 3：定义目标用户（1-2 小时）**
- 参考 Proto Persona（见 6.4）
- 明确优先级与决策权

**阶段 4：定义成功指标（1-2 小时）**
- 主/次/护栏三类指标
- 基线数据 + 目标值 + 测量方式

**阶段 5：起草方案与用户故事（4-8 小时）**
- 方案概述（选项 + 推荐）
- 核心用户故事（见 7.5）
- **质量门 2**：工程评审方案可行性

**阶段 6：评审与迭代（1-2 天）**
- 跨职能评审（工程、设计、数据、市场、客户成功）
- 收集反馈 → 修订

**阶段 7：定稿与签署（2-4 小时）**
- 确认范围外、依赖、风险
- 利益相关方签字确认

**阶段 8：交付与跟踪（持续）**
- 拆分为用户故事（见 7.6）
- 跟踪指标，按数据迭代 PRD

### PRD 模板骨架 / PRD Template Skeleton

```markdown
# [功能名] PRD / [Feature Name] PRD

## 执行摘要 / Executive Summary
[3-5 句：做什么、为什么、成功指标、范围]

## 问题陈述 / Problem Statement
[用户 + 问题 + 影响（见 7.4）]

## 目标用户 / Target Users
[画像 + 优先级 + 决策权]
```

## 7.3 问题框架画布 / Problem Framing Canvas

**触发词**：问题框架、问题重构、HMW、我们如何能、MITRE、重新框定

**适用场景**：团队对问题理解不一致时；方案讨论陷入僵局（回到问题层面）；问题太宽泛或太狭窄需要重构；重大决策前的系统化问题检查。不适用：问题已清晰（直接定义方案）、琐碎问题、需要快速决策的紧急情况。

### 核心概念：MITRE 三阶段 / Core Concept: The MITRE Three Phases

**向内看（识别假设与偏见）**：
- 列出我们对该问题已有的假设
- 识别认知偏见（确认偏差、现状偏差、锚定效应）
- 质疑问题本身的措辞

**向外看（谁受影响）**：
- 谁经历这个问题？（直接用户、间接用户、利益相关方）
- 谁有资源解决它？（决策者、技术、资金）
- 谁的利益相关？（竞品、监管、合作伙伴）

**重构（多角度框定）**：
- 从每个受影响方视角重述问题
- 用 HMW（我们如何能）句式生成多个问题框架
- 选择最有杠杆的框架

### HMW 陈述模板 / HMW Statement Template

```
我们如何能 [动词] [对象]，从而 [期望成果]，同时 [约束条件]？
```

示例：
- 弱："我们如何能做一个更好的发票工具？"（方案优先）
- 强："我们如何能帮小企业主减少花在回款上的时间，同时不显得咄咄逼人？"（成果 + 约束）

### 应用流程（交互式，8 个问题）/ Application Flow (interactive, 8 questions)

**向内看（Q1-3）**：
1. "我们对这个问题的现有假设是什么？"（列出假设 + 挑战）
2. "哪些认知偏见可能在影响我们的框定？"
3. "问题现在的措辞是否限制了方案空间？"

**向外看（Q4-6）**：
4. "谁直接经历这个问题？他们如何受影响？"
5. "谁间接受影响？（利益相关方、合作伙伴、竞品）"
6. "谁有权解决或阻塞解决方案？"

**重构（Q7-8）**：
7. "从每个受影响方的视角，问题分别是什么？"
8. "哪个 HMW 框架最有杠杆？为什么？"

### 输出模板 / Output Template

```markdown
# 问题框架画布 / Problem Framing Canvas

## 当前问题陈述 / Current Problem Statement
[原始陈述]

## 假设与偏见 / Assumptions & Biases
| 假设 | 挑战 | 偏见类型 |
|---|---|---|

## 受影响方 / Affected Parties
| 角色 | 问题体验 | 利益 |
|---|---|---|

## 重构的 HMW 框架 / Reframed HMW
1. 我们如何能 [……]？（视角 A）
2. 我们如何能 [……]？（视角 B）
3. 我们如何能 [……]？（视角 C）

## 选择 / Options
[选中的框架 + 理由]
```

### 常见陷阱 / Common Pitfalls

- 直接跳到方案（"我们要做 X"——先框定问题）
- 单一视角（只从自己团队视角看问题）
- HMW 太宽泛（"我们如何能拯救世界"）或太窄（"我们如何能改按钮颜色"）
- 一次框定永不回顾（问题会随学习演变）

## 7.4 问题陈述 / Problem Statement

**触发词**：问题陈述、痛点描述、共情叙事、problem statement

**适用场景**：PRD/路线图/提案中需要正式问题陈述时；对齐团队对问题的理解；为设计/工程提供问题上下文。

### 核心概念：共情叙事框架 / Core Concept: Empathy Narrative Framework

**结构**：
- **我是** [角色描述]
- **试图** [要完成的任务]
- **但是** [遇到的阻碍]
- **因为** [根本原因]
- **这让我感到** [情感影响]

### 应用流程 / Application Flow

**步骤 1：收集背景**——用户研究洞察（访谈、数据、工单）、画像定义、当前替代方案。缺背景先做发现（见 6.2、6.3）。

**步骤 2：撰写共情叙事**：

```markdown
## 问题陈述 / Problem Statement

### 叙事 / Narrative
[角色] 是 [背景描述 2-3 句]。
他/她 试图 [任务]，但是 [阻碍]，
因为 [根本原因]，这让他/她感到 [情感]。

### 上下文约束 / Context Constraints
- 影响范围：[多少用户/哪些场景]
- 当前状态：[现在如何解决]
- 频率与强度：[多久一次、多痛]
```

**示例**：
"Sarah 是管理 10 个客户项目的自由设计师。她试图准确追踪每个客户的付款状态，但发票分散在电子表格和邮件里，因为缺乏集中管理工具，这让她每月花费 8 小时追款并持续焦虑现金流。"

**步骤 3：提炼最终陈述**：

```markdown
[用户细分] 需要 [核心需求]，因为 [根本原因]，以便 [期望结果]。
```

**步骤 4：质量检查**：
- 共情？（像用户的真实声音）
- 具体？（含具体数字与场景）
- 问题导向？（不预设方案）
- 已验证？（基于真实研究而非假设）

### 常见陷阱 / Common Pitfalls

- 方案伪装成问题（"需要 X 功能"是方案，不是问题）
- 太抽象（"用户需要更好的体验"——什么体验？）
- 无情感维度（问题是人的问题，不是流程问题）
- 无数据支撑（"很多人有这个问题"——多少人？）

## 7.5 用户故事 / User Story

**触发词**：用户故事、user story、As a、验收标准、Gherkin

**适用场景**：把需求拆为可交付的用户故事；为故事编写验收标准；团队对齐"做什么 + 怎么算完成"。

### 核心概念：两种格式 / Core Concept: Two Formats

**Mike Cohn 三要素**：
```
作为 [角色]，我想要 [功能]，以便 [收益]
```
例："作为远程团队的项目经理，我想要任务分配时收到通知，以便及时响应避免延误"

**Gherkin 验收标准**：
```
场景：[场景名]
  给定 [前提条件]
  当 [触发动作]
  那么 [期望结果]
```
例：
```
场景：任务分配通知
  给定 我是项目"网站改版"的成员
  当 我被分配一个任务
  那么 我会收到即时通知
```

### 质量标准（INVEST）/ Quality Criteria (INVEST)

- **独立（Independent）**：可独立排期开发
- **可协商（Negotiable）**：留有协作发现空间
- **有价值（Valuable）**：用户可观察的价值
- **可估算（Estimable）**：团队能相对估算
- **小（Small）**：一个迭代可完成
- **可测试（Testable）**：有清晰验收标准

### 写作规则 / Writing Rules

- 单 When 单 Then：一个场景只有一个触发和一个结果
- 用用户语言：不用技术术语（"系统调用 API"不是用户故事）
- 聚焦行为：描述行为变化，不描述实现
- 每故事一个核心场景 + 若干边界场景

### 常见陷阱 / Common Pitfalls

- 技术任务伪装成用户故事（"重构数据库"——不是，是技术任务）
- 验收标准缺失（无法测试 = 未完成定义）
- 故事太大（超过一个迭代 = epic，需拆分见 7.6）
- 预先写全部故事（用户故事应随迭代展开）

## 7.6 用户故事拆分 / User Story Splitting

**触发词**：故事拆分、epic 拆解、垂直切片、拆分模式

**适用场景**：epic/大故事需要拆为可交付故事；故事超过一个迭代；需要保持垂直切片（端到端价值）而非水平切片（技术层）。

> 本技能与 2.5 Epic 拆解顾问同源（Richard Lawrence 方法论），2.5 侧重 epic 层面流程，本技能侧重故事层面模式速查。

### 核心概念 / Core Concepts

垂直切片 = 触碰多个架构层并交付可观察用户价值的工作。水平切片（"前端故事"+"后端故事"）是反模式。

### 八种拆分模式（Richard Lawrence）/ Eight Splitting Patterns (Richard Lawrence)

1. **工作流步骤**——细的端到端切片（不是逐步切）
2. **业务规则变体**——不同规则 = 不同故事
3. **数据变体**——不同数据类型/结构
4. **数据录入方式**——先简单 UI，后复杂 UI
5. **重大工作量**——"先实现一个 + 其余后续加"
6. **外部依赖**——拆出依赖部分，其余先行
7. **DevOps 步骤**——部署/监控/回滚能力拆分
8. **微小发现行动（TADs）**——拆出限时调查故事

### 元模式 / Meta-Patterns

1. 识别核心复杂度
2. 列出所有变体
3. 变体缩减为一个完整切片
4. 其他变体做成独立故事

### 拆分验证（5 项）/ Split Verification (5 checks)

拆分后逐项检查：
- [ ] 每个故事都交付用户可观察价值？
- [ ] 每个故事独立可排期？
- [ ] 每个故事一个迭代内可完成？
- [ ] 每个故事有验收标准？
- [ ] 拆分没有制造隐藏依赖？

### 示例 / Example

**原始故事**："作为管理员，我想要完整的报表功能"
**拆分后**：
1. "作为管理员，我想要查看本周活跃用户数"（核心切片）
2. "……按渠道筛选"（数据变体）
3. "……导出 CSV"（数据录入方式）
4. "……定时邮件发送"（工作流步骤）
5. "……报表加载性能达到 <2 秒"（延迟性能——可拆为技术任务）

## 7.7 用户故事地图 / User Story Mapping

**触发词**：故事地图、story map、Jeff Patton、用户旅程排序、发布切片

**适用场景**：从用户旅程组织产品积压；对齐团队对整体体验的理解；规划发布顺序（最小可用骨架）；发现遗漏的场景。

> 本技能合并自 user-story-mapping（方法框架）与 user-story-mapping-workshop（交互式工作坊）。

### 核心概念：二维地图 / Core Concept: Two-Dimensional Map

**横轴（主干）**：用户旅程的活动与步骤（按时间顺序）
**纵轴（优先级）**：每步下的故事按重要性/发布顺序排列

```
         活动 1          活动 2          活动 3
    ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
    │ 步骤 1       │  │ 步骤 1       │  │ 步骤 1       │
    │  故事 A(核心) │  │  故事 D(核心) │  │  故事 G(核心) │
    │  故事 B      │  │  故事 E      │  │  故事 H      │
    │  故事 C      │  │  故事 F      │  │  故事 I      │
    └─────────────┘  └─────────────┘  └─────────────┘
     ↑ 骨架（第一发布）     ↑ 第二发布           ↑ 第三发布
```

### 层级分解 / Hierarchy Breakdown

**Segment（细分）→ Persona（画像）→ Narrative（叙事）→ Activities（活动）→ Steps（步骤）→ Tasks（任务）**

- 地图始于用户旅程的活动与步骤（横轴）
- 每个步骤下挂用户故事（纵轴）
- Walking Skeleton（行走骨架）= 覆盖完整旅程的最小故事集，是第一个发布目标

### 应用流程（交互式工作坊，5 个自适应问题）/ Application Flow (interactive workshop, 5 adaptive questions)

**步骤 0：准备**——确定画像与场景、收集故事素材（用户研究、访谈、现有积压）。

**问题 1：范围**——"地图覆盖什么？（整个产品 / 一个流程 / 一个史诗）"

**问题 2：用户**——"谁走这条旅程？（画像 + 数量）"

**问题 3：骨架**——"旅程的主要活动有哪些？（按时间顺序）"→ 横轴

**问题 4：任务**——"每个活动下用户做什么？（步骤细分）"→ 展开

**问题 5：发布切片**——"哪些故事构成第一个可用版本（Walking Skeleton）？之后如何切片？"→ 纵轴分组

### 工作坊输出模板 / Workshop Output Template

```markdown
# 用户故事地图：[产品/流程] / User Story Map: [product/flow]

## 画像与场景 / Personas & Scenarios
[画像 + 覆盖场景]

## 旅程主干（横轴）/ Journey Backbone (horizontal axis)
| 活动 | 步骤 | 故事（按优先级↓） |
|---|---|---|
| [活动 1] | [步骤 1.1] | [故事 A] [故事 B] |
| | [步骤 1.2] | [故事 C] |
| [活动 2] | [步骤 2.1] | [故事 D] |

## 发布切片（纵轴分组）/ Release Slices (vertical grouping)
- **发布 1（Walking Skeleton）**：故事 A、D、G（完整旅程最小集）
- **发布 2**：故事 B、E、H
- **发布 3**：故事 C、F、I
```

### 常见陷阱 / Common Pitfalls

- 只按优先级排列（丢了旅程上下文）
- 无 Walking Skeleton（第一版不完整，无法端到端验证）
- 地图做一次就归档（应随学习持续更新）
- 与用户故事拆分脱节（地图上的故事仍需按 7.6 拆分）

# 第八部分：职业成长 / Part 8: Career Growth

## 8.1 AI 塑造能力评估 / AI-Shaped Readiness Advisor

**触发词**：AI 能力、AI-Shaped、AI 时代产品经理、AI 就绪度、2026 产品能力

**适用场景**：评估自己或团队的 AI 时代产品能力现状；识别优先级最高的成长方向；制定 4 周行动计划；面试/晋升准备中展示 AI 能力。

### 核心概念：AI-First vs AI-Shaped / Core Concept: AI-First vs AI-Shaped

- **AI-First**：把 AI 作为产品核心（"我们做一个 AI 产品"）——是产品方向选择
- **AI-Shaped**：产品经理自身能力形状——在 AI 世界里高效工作的能力组合。**关键认知**：AI-Shaped 不等于会写提示词或会用工具，而是改变工作方式的五种能力。

### 五项能力（2026 PM 核心能力）/ Five Capabilities (2026 PM Core Competencies)

1. **上下文设计（Context Design）**——为 AI 设计精确、无歧义的工作上下文。AI 输出质量 = 输入上下文质量。这是基础能力，其他四项都依赖它
2. **代理编排（Agent Orchestration）**——设计和管理多个 AI 代理协作完成复杂工作流
3. **成果加速（Outcome Acceleration）**——用 AI 把从洞察到成果的时间压缩
4. **团队-AI 协作引导（Team-AI Facilitation）**——引导人类与 AI 组成的混合团队高效协作
5. **战略差异化（Strategic Differentiation）**——在 AI 商品化的世界里找到人+AI 结合的独特价值

### 成熟度四级 / Four Maturity Levels

每项能力按 1-4 级评估：
- **1 级（认知）**：理解概念，未实践
- **2 级（应用）**：在指导下可用于简单场景
- **3 级（熟练）**：独立应用于复杂场景
- **4 级（精通）**：能教别人、能设计新方法

### 交互评估流程（13 个问题）/ Interactive Assessment Flow (13 questions)

**背景部分（8 个问题）**：工作场景、团队 AI 使用现状、已有工具、时间投入、组织支持、失败经历、成功经历、瓶颈感知。

**评分部分（5 个问题）**：逐项能力自评（选项 = 4 级成熟度描述 + 具体例证）。

**依赖逻辑**：若上下文设计 <3 级，优先补它（其他能力都会受限）。

### 输出：5 个优先级行动方案 / Output: 5 Priority Action Plans

按评估结果给出 3-5 个编号行动建议，每个含 4 周计划：
- 第 1 周：学习 + 找到真实场景
- 第 2 周：最小实践（用 PoL 探针思路）
- 第 3 周：复盘 + 调整
- 第 4 周：固化成果 + 分享

### 常见陷阱 / Common Pitfalls

- 把"会用 ChatGPT"当 AI-Shaped（工具使用 ≠ 能力）
- 五项能力平推（应聚焦 1-2 项优先突破）
- 跳过上下文设计直接练编排（地基不稳）
- 无真实场景练习（能力靠实践不靠阅读）

## 8.2 上下文工程顾问 / Context Engineering Advisor

**触发词**：上下文工程、上下文填充、AI 上下文、context engineering、记忆架构

**适用场景**：AI 输出质量不稳定时诊断根因；判断该"给更多上下文"还是"修结构"；设计 AI 系统的上下文边界与记忆架构；团队 AI 工作流优化。

### 核心概念：上下文填充 vs 上下文工程 / Core Concept: Context Stuffing vs Context Engineering

- **上下文填充（Context Stuffing）**：不断把更多资料塞给 AI，期待输出变好——通常是给 AI 输出质量问题打补丁
- **上下文工程（Context Engineering）**：系统设计"AI 需要什么上下文、谁拥有它、如何更新"，从结构上保证质量

### 上下文填充的 5 个标志 / Five Signs of Context Stuffing

1. 提示词越来越长，但输出质量停滞
2. 每次会话都重新粘贴同样的背景资料
3. AI 回答的"遗忘"靠手动重述解决
4. 团队成员各自维护不同的上下文版本
5. 输出错误被当作"提示词问题"反复调参

### 5 个诊断问题 / Five Diagnostic Questions

1. **这个上下文支持什么决策？**——不服务决策的上下文是噪音
2. **检索能否替代持久化？**——能检索到的就不必预填
3. **谁拥有上下文边界？**——边界清晰到每个人知道该放什么进来
4. **排除它会失败什么？**——最小化上下文而不破坏关键路径
5. **修结构还是回避？**——问题出在结构设计还是使用方式

### 双层记忆架构 / Two-Layer Memory Architecture

- **工作层（短期）**：当前任务相关上下文，任务结束即清理
- **持久层（长期）**：跨任务稳定的知识（产品决策、用户洞察、团队规范），定期审查更新

### Research → Plan → Reset → Implement 循环 / Research → Plan → Reset → Implement Loop

1. **研究（Research）**：梳理现有上下文使用，找出重复粘贴、版本漂移、输出失败模式
2. **规划（Plan）**：设计上下文结构：哪些进持久层、哪些检索获取、边界归谁
3. **重置（Reset）**：清理冗余上下文，重建统一版本
4. **实施（Implement）**：落地结构与流程，设置定期审查

### 效率公式 / Efficiency Formula

**效率 = (准确率 × 一致性) / (Token 数 × 延迟)**

上下文工程的终极目标不是"给更多"，而是用最小上下文达到最高质量。

### 常见陷阱 / Common Pitfalls

- 把输出问题一律归因"上下文不够"（先诊断再补料）
- 上下文无所有权（谁都改，没人负责）
- 持久层无审查（知识过期，错误被固化）
- 检索替代品缺失（该检索的非要预填）

## 8.3 总监晋升辅导 / Director Readiness Advisor

**触发词**：晋升总监、PM 转总监、总监面试、新任总监、总监转型

**适用场景**：3-12 个月内准备晋升总监；总监面试准备（内部/外部）；新任总监前 6 个月；总监角色 12 个月以上诊断问题。基于 2.1 海拔与地平线框架。

### 四种转型情境 / Four Transition Scenarios

1. **准备晋升**——仍在 PM 角色，积极向总监发展
2. **面试中**——内外部搜索进行中
3. **新上任**——最近晋升/入职（前 6 个月）
4. **重新校准**——担任总监一段时间，有不顺

**核心规则**：不要用"新上任"的建议套在两年老总监身上，也不要用"准备"建议套在面试中的人身上。

### 交互流程（1 诊断问题 + 3 自适应问题）/ Interaction Flow (1 diagnostic + 3 adaptive questions)

**问题 1：你在哪？**——四种情境之一（见上）

**分支 1：准备晋升**
**问题 2**："移动前你最想补的差距是什么？"
1. **思维海拔**——仍默认直接解决客户问题而非设计系统
2. **利益相关方导航**——组织政治、高管动态、跨职能影响力吃力
3. **战略叙事**——无法在领导对话中令人信服地连接工作与公司战略
4. **方向创造**——等待上方清晰而不是为团队创造清晰
**问题 3**："你的跑道——距离行动多远？"（6+ 月 / 3-6 月 / 已在申请）

**分支 2：面试中**
**问题 2**："面试情境？"（内部晋升 / 外部搜索 / 两者并行）
**问题 3**："面试准备最想练什么？"
1. **内化框架**——深度理解海拔与地平线模型，能流利表达
2. **构建故事**——概念理解但难连接自身经验
3. **演练回答**——用框架预演常见总监面试题
4. **识别差距**——哪些转型区还没展示过，如何诚实应对

**分支 3：新上任**
**问题 2**："最紧迫的挑战？"
1. **还是 PM 思维**——默认直接解决问题而非引导他人解决
2. **英雄综合征**——知道该放权但忍不住跳进去
3. **方向不明**——等不来上方战略清晰，团队漂移
4. **利益相关方错位**——时间花在工程师身上，而非同级与高管
**问题 3**："团队情境？"（继承既有团队 / 组建新团队 / 混合）

**分支 4：重新校准**——诊断哪个转型区持续制造摩擦（见 2.1 四区 + 失败模式）。

### 核心建议（分支精选）/ Core Advice (selected branches)

**准备晋升**：
1. 重新框定 1 对 1：从汇报战术进展转为提问战略问题："我的工作如何连接公司今年的目标？"
2. 现在就练级联习惯：挑一个公司优先项，写一页翻译，非正式分享
3. 审计英雄综合征：两周内记录"跳进去解决本可教练解决"的次数
4. 别过度表现总监思维：全力做好当前 PM 角色，就绪度体现在工作质量

**面试**：
1. 每个转型区备一个具体故事（思维海拔、角色转变、方向创造……）
2. 用总监语言重述 PM 战绩：不说"我上线了 X"，说"团队面对的战略问题是 X，我是这样思考组合取舍的"
3. 诚实应对差距："这是差距，这是我如何补，这是前 90 天我重点学什么"

**新上任**：
1. 本周就运行上下文级联（见 2.1）——不等待完美清晰
2. 诊断英雄综合征触发点，建立放权仪式
3. 时间再分配：从"与工程师泡在一起"转向"与同级和高管建立节奏"

## 8.4 VP/CPO 晋升辅导 / VP/CPO Readiness Advisor

**触发词**：VP 晋升、CPO 晋升、总监转 VP、高管转型、产品高管

**适用场景**：总监准备 VP/CPO 转型；评估 VP/CPO 机会（问 CEO 什么问题）；新上任前 6 个月；高管角色不顺重新校准。

### 核心概念 / Core Concepts

**Three Ps 框架**：高管层责任同时扩展到三个维度：
- **产品（Product）**——组合决策、路线图战略、产品家族一致性
- **实践（Practice）**——工作如何完成：流程纪律、执行一致性、跨职能运营节奏
- **人员（People）**——此层级的核心：组织结构、人才匹配、培养领导者、设定并检查预期

多数总监强于产品、实践尚可，**人员**维度（不是管理个人而是经营组织系统）是 VP/CPO 转型最常见的断点。

**赋权神话**：最常见的晋升误解——"到了那里我终于被赋权了"。现实：约束不会消失，只会变形。PM 的魔方是 3×3，总监 5×5，VP 7×7，CPO 9×9。每个决策的爆炸半径指数级扩大。

**VP → CPO 范式转变**：
- **VP 心态**："我们要发布什么？产品组合表现如何？路线图是什么？"
- **CPO 心态**："我们负责什么业务成果，产品组织如何达成？"
- 实际后果：高管论坛停止使用产品语言（功能、路线图、用户故事、冲刺），改用商业语言（ROI、收入、留存、毛利、EBITDA）；主要"客户"可能转向投资人/买方；最重要的团队变成高管班子（CEO、CFO、CRO、CMO）

**时间地平线扩展**：

| 层级 | 短期 | 长期 |
|---|---|---|
| 个人贡献者 | 冲刺 | 季度 |
| 总监 | 季度 | 1-2 年 |
| VP | 1-2 季度 | 3 年 |
| CPO | 1-2 季度 | 3-5 年 |

**高管联盟**：在 VP/CPO 层级，高管团队成为主要运作环境，联盟不是可选项。没有联盟你就是"行尸走肉"——高管可以在会上支持、会外拆台。联盟建设：每周与同级高管接触（不是年度路线图评审）；主动沟通取舍（"这季度你拿不到 X 因为 Y，这对业务最好"）；决定宣布前先拉人上船；理解每个同级的真实优先项（不只是口头声称的）。

### 四种转型情境 / Four Transition Scenarios

1. **准备起跳**——仍是总监，积极构建 VP/CPO 能力
2. **评估/面试中**——活跃搜索或评估具体机会
3. **新上任**——最近进入 VP/CPO 角色（前 6 个月）
4. **重新校准**——在角色中一段时间，有不顺

### 交互流程要点 / Interaction Flow Essentials

**问题 1**：你在 VP/CPO 旅程的哪里？（四种情境）

**准备起跳分支**：
- 哪个 P 是最大发展区？（产品/实践/人员/都薄）
- 对高管动态的视角？（接触有限/偶尔/增长中/近距离）

**评估分支**：
- 流程位置？（早期探索/活跃面试/接近 offer）
- 最想练什么？（展示高管思维/评估角色/准备战略演示）

**新上任分支**：最紧迫挑战？（产品语言惯性/联盟缺失/战略不清晰/团队问题）

**核心建议**：
1. 通过现任 VP/CPO 的镜头研究 Three Ps：他们时间花在哪？硬决策由哪个 P 驱动？直接问"每个 P 占你时间多少百分比？"
2. 现在就认领一个人事问题：主动带队重组、把住招聘标准、处理人才错配——技能靠练不靠学
3. 刻意建立一个高管关系：找一个与你的 VP 有常规互动的同级，找理由建立工作关系
4. 用顾问的评估分支做面试准备：CEO 面试问题暴露你需要驾驭的东西

## 8.5 高管入职手册 / Executive Onboarding Playbook

**触发词**：30-60-90、高管入职、VP 入职、CPO 入职、新任产品领导、评估 CPO offer

**适用场景**：新任 VP/CPO 前 90 天；评估 CPO offer（接受前问什么）；诊断刚接手组织；2 个月时验证所学再行动。

### 核心概念 / Core Concepts

把 VP/CPO 转型的前 90 天结构化为诊断过程，而非执行冲刺。**高管产品领导转型最常见的失败是未理解就行动**——在建立可辩护决策的证据基础前就改结构、换人、宣布战略。

三阶段：**诊断（月 1）→ 验证（月 2）→ 凭证据行动（月 3）**。跳阶段不会加速结果——只会保证昂贵的反复。

### 顾问心态 / Advisor Mindset

像外聘顾问一样进入角色——先评估组织，再承担改变它的责任：
- **先观察后诊断**：第一周别凭第一印象形成观点
- **先提问后宣布**："帮我理解这怎么运作"比"这是我们要做的改变"更有力
- **理解方向盘如何连接舵**：纸上看起来一套、实际运作另一套的系统与关系，先画清现实
- **别拉大红开关**：走进没操作过的电厂看到大红开关，你不会拉它。同样的逻辑适用于继承的组织结构、流程、汇报线与团队构成——先理解它们控制什么

**提前谈判**：告诉老板和同级，月 1 明确是学习期；首个重大建议月 2 提出。经历过转型的高管会尊重这一点；第一周就要行动的高管是一个值得注意的信号。

### 隐性战略 / Implicit Strategy

VP/CPO 层级，大量重要战略从不完整落笔。它存在于：CEO 脑中（由你没参与的对话塑造）、董事会动态与投资人偏好、昨晚的高管晚餐、创始人间的私下谈话、资深领导视为理所当然的部落知识。

这不是机能障碍——这是每个组织的运作方式。把书面战略当完整战略会让你快速陷入麻烦。前 90 天的工作就是浮出隐性层：
- 问间接问题："这里的历史是什么？""我们怎么走到这个方案的？""我们以前试过什么失败了？"
- 让信息找到你：想塑造新领导视角的人会主动找你。接见他们，记笔记
- 与老板现实校准："我从组织听到的是 X，这和你告诉我的不同。帮我理解。"——这不是对抗，这是三角验证真相

### 证据体 / Evidence Base

月 3 及以后的每个重大决策都应建立在月 1-2 收集的证据体上：
- 每次诊断对话的详细笔记
- 跨多个独立来源的模式（不只一个嗓门大的人）
- 与经理和关键同级完成的现实校准
- 什么有效、什么坏了、为什么的清晰图景

证据体是自信决策与猜测的分界线，也让艰难决策对团队、同级、董事会都可辩护。

### 人员评估：两类情况 / People Assessment: Two Cases

**璞玉（Diamonds in the rough）**——有能力但被低估、没有伯乐的人。几乎每个组织都有。月 1-2 靠倾听发现："她真有才华但没人给她难题"；或注意谁在诊断访谈中给你最有用、最不加修饰的信息。他们成为关键早期盟友。

**错位强人（Strong people in wrong roles）**——不是弱绩效者；是优势与当前职责错配的人。快速增长、并购、论资排辈的组织常见。前销售转 PM（因为懂产品）、需要教练的团队却配了杰出个人贡献者。需要诚实而关怀的对话——可教练就培养，否则找其他角色，或体面分手。三种结果都好过放任错位。

### Phase 0：入职前（评估 offer 时）/ Phase 0: Before Joining (Evaluating the Offer)

**向招聘 CEO 问的五个问题**：
1. "你对产品组织前 90 天和第一年的预期是什么？"——早期暴露不切实际的转型时间线。红旗："我希望 Q2 前路线图全面重做。"
2. "你产品团队的全明星是谁，为什么？"——暴露 CEO 的认知与偏见。他们常错，但了解心智模型很重要
3. "谁有差距，为什么？"——CEO 认为组织的弱点是什么？准确吗？
4. "我该提前了解哪些约束？"——财务、组织、市场。接受前理解你的实际自由度
5. "这个角色一年后成功的标准是什么？"——迫使具体化。模糊答案（"转型产品文化"）是红旗；具体答案（"85% 按时交付、两个新企业客户、一个重建团队"）可行

**改变决策的红旗**：
- "你不能动现有产品路线图"——开始前就失去基本权力
- "我们需要你六个月转型组织"——注定失败
- CEO 人才评估与你在其他对话中的发现不一致

### 三阶段应用 / Three-Phase Application

**阶段 1：诊断（月 1）——建立证据体，理解现实而非官方版本**
- 访谈所有人：直接下属 30 分钟对话 + 关键跨职能同级（CRO、CFO、CMO、工程领导）+ PM 样本。问题集：什么在有效运作我该理解并保护？什么不运作你一直希望有人修？我需要知道什么官方简报里不会说？该找谁谈？
- 让人找你：有价值的信息常来自主动约见新领导的人。他们有议程——浮出它、评估它、注意信号
- 详细笔记：每场对话，记内容也记背景（谁说的、他们可能的动机、多个独立来源是否一致）
- 抵抗行动：月 1 看到明显坏了的东西，本能是修。抵抗。你还没有上下文知道它为什么坏、之前修复为何失败、它连接着什么。记入证据日志
- 交付物：组织现实的详细笔记本（尚未解读）

**阶段 2：验证（月 2）——浮出模式，挑战新结论，识别人员情况**
- 与老板现实校准："我从多人听到 X，与我进来时的理解不同，帮我理解历史"
- 映射隐性战略：直接问"组织在困难时实际优化什么？"答案通常与使命宣言不同
- 完成人员评估：谁是璞玉（如何给更多空间）、谁错位（正确的对话什么样）、谁真的教不到组织需要的层级（什么时间线合适）
- 识别 3-5 个最高杠杆变更：不是完整转型计划，是三个到五个最能提升组织效能的特定变更——成为月 3 议程
- 交付物：解读过的组织评估 + 人员地图 + 初步战略优先项

**阶段 3：凭证据行动（月 3）——开始基于证据体做决策，引入结构与方向，不是转型**
- 分享组织评估：别保密。对老板和直接下属："我学到了这个组织如何运作、哪里强、哪里需要发展。这是我下季度的初步计划。"透明建立信任，行动前浮出分歧
- 运行第一次上下文级联（见 2.1）：即使公司战略仍模糊，给团队你的最佳翻译并承诺持续完善——团队一直在等上下文
- 开始人事对话：璞玉给延伸任务或扩大范围；错位者直接诚实的对话；离开的以诚实与关怀开始，而非回避
- 刻意建立高管联盟：与 CRO、CFO、CMO 的每周对齐节奏，确保他们理解产品优先项与取舍。别等他们找上门

### 常见陷阱 / Common Pitfalls

- 月 1 就宣布战略/改组织（证据体缺失下的昂贵错误）
- 只信官方渠道信息（隐性战略才是真相）
- 凭单一声源形成结论（要跨独立来源的模式）
- 把"受欢迎"当"有效"（尊重来自清晰与硬决策）
